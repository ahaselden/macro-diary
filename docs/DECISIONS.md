# Decisions log

Short records of non-obvious choices and **why**, in the order they were made. Anything marked **(made without the owner)** was decided while the owner was away and is the first thing to review or overrule. Format: context → decision → consequences.

---

## D1. Vanilla ES modules, no framework, no bundler
**Context:** The app was one 727-line HTML file; a meal planner is coming. **Decision:** split into native ES modules served as-is (no build step, no dependencies). **Why:** the app is small; a bundler/framework adds tooling, upgrade chores and a build in CI for little gain, and GitHub Pages serves static files fine. **Consequences:** `index.html` no longer works from `file://` (browsers block module loading) — use `npm start`. Revisit (Vite + TypeScript) if the UI layer grows past what hand-written render functions handle comfortably.

## D2. Strict layers: `ui → services → domain → core`
**Decision:** `core/` has no dependencies; `domain/` is pure logic that may import only `core/` (constants, format, dates) and itself; `services/` talks to the outside world and may import `domain/` and `core/`; `ui/` is the only layer that touches the DOM. **Why:** pure `domain/` code is trivially unit-testable in Node and reusable by features that don't exist yet (recipes and shopping lists reuse the units/density logic). Violations are checked in review (`.claude/agents/regression-reviewer.md`).

## D3. Golden-file tests captured from the original app
**Decision:** before moving any code, the *old* code was run in a browser against a deterministic fixture (`tests/fixtures/`) and its outputs saved (`tests/golden/`). New modules must reproduce them exactly. **Why:** a refactor's main risk is silently changing behaviour; the old code is the best specification we have, and capturing it mechanically beats re-deriving expectations by hand. **Consequences:** `tests/golden/reports.json` is large (~700 KB) because it holds full CSV outputs; acceptable for a byte-exact check. If behaviour is *intentionally* changed later, regenerate the affected golden file in the same commit and say why.

## D4. Application state is one mutable object (`state`), replaced via `replace()`
**Decision:** `core/store.js` exports a single `state` object that is mutated in place; whole-state swaps (restore/wipe) go through `replace()`, which keeps the same object identity. **Why:** every module can hold a reference without stale-copy bugs, and there is exactly one place that touches `localStorage`. `createStore(storage)` takes the storage as a parameter so tests use a fake.

## D5. Storage key stays `macrodiary.v1`; shape changes are versioned
**Decision:** the key never changes. A `schemaVersion` field plus `migrate()` handle shape changes. **Why:** the key is where existing users' phones/PCs keep their diary; changing it would orphan their data. Old data without `schemaVersion` is treated as v1 and stamped.

## D6. Domain functions return new state instead of mutating (`mergeBackup`)
**Decision:** `mergeBackup(state, backup)` returns a new object; the caller `replace()`s and saves. **Why:** pure functions are easier to test and reason about, and the caller decides when to persist.

## D7. Agents extract modules in parallel but only create *new* files
**Decision:** each extraction agent wrote only its own new module and test; the main session did all edits to `index.html`. **Why:** no merge conflicts, and the single integration point stays under one owner. Each agent's report was verified by re-running the whole suite and grepping the layer rule, not taken on trust.

## D8. Bugs found during a refactor are logged, not fixed
Reported by extraction agents/reviewer and kept as-is so behaviour stays identical; collected in `docs/KNOWN-ISSUES.md` for deliberate fixing later.

## D9. Last-writer-wins per record, with tombstones, for merging (restore now, sync later) — *made without the owner*
**Context:** the old "Merge" only *added* entries missing locally. That can't carry an edit ("I fixed the grams on my phone") or a deletion ("I removed that entry") from one device to another, and sync needs both. **Decision:** every record (diary entry, custom food, saved measure; settings as one record) carries `updatedAt`; the newer one wins; a deletion writes a **tombstone** `state.tombstones[id] = deletedAt`, which beats any version of the entry last edited before it. Implemented in `js/domain/merge.js` as a pure `mergeStates(a, b)`; entry changes go through `js/domain/entries.js` (`addEntry/updateEntry/removeEntry`) so they are always stamped. **Why LWW per record rather than per day or per field:** a day is edited from several devices (breakfast on the phone, lunch on the PC) so day-level LWW would lose entries; per-field LWW adds bookkeeping with no real benefit for records this small. **Why tombstones:** without them a deleted entry reappears from whichever device hasn't heard of the deletion yet. **Guarantees (property-tested over 300 random state triples):** commutative, associative, idempotent — devices converge in any sync order. **Trade-offs:** device clocks are trusted (a phone with a wrong clock can win or lose edits unfairly; acceptable for one person's devices); tombstones accumulate until `pruneTombstones` (not yet called automatically); equal timestamps are broken by comparing the serialised records (arbitrary but identical everywhere).

## D10. What does *not* sync — *made without the owner*
`theme`, `apiKey` and `recent` stay per-device. Theme is a per-device preference (dark on the phone, light on the PC). The USDA key is a credential the owner should paste per device rather than have copied to a cloud store. `recent` is derived convenience data whose list order would otherwise make every sync "change" something and never settle. Goals, weight unit and database toggles sync as one settings record. Revisit if the owner wants the key or theme synced.

## D11. Schema v3 and sanitising on every load/restore
`core/schema.js` (pure, so `domain/` can use it) holds `defaults`, `migrate`, `sanitize`. v3 adds `tombstones` and `settingsUpdatedAt`; **existing entries are not rewritten** — a missing `updatedAt` simply means 0 ("older than any real edit"), so upgrading changes nothing a user can see and cannot lose data (tested against the original fixture). `sanitize` forces untrusted fields (goals, units, theme, tombstones…) to safe types because a restored file reaches the HTML through them (KNOWN-ISSUES #1).

## D12. "Restore → Merge" prefers this device on a tie
Old backups have no timestamps, so every record ties. For *restore* (a human deliberately importing a file) the device keeps its own version on a tie (`preferLocal`), matching the old behaviour; for *sync* the symmetric tie-break is used because it must not depend on which device runs the merge. The test suite proves a restore-merge still brings in exactly the data the original merge did (golden), and that it now also applies newer edits and deletions found in the backup.

## D13. One schema bump (v4) for all planner data, added before any planner feature — *made without the owner*
**Decision:** `recipes`, `plan` and `shopping` were added to the schema, sanitiser, merge and sync records **in one step, before** the recipe/plan/shopping features, so those features never need their own migration and are *born syncable*. **Shapes:** `recipes: {id: recipe}` (record = one recipe, tombstones apply); `plan: {YYYY-MM-DD: {updatedAt, slots:{Breakfast,Lunch,Dinner,Snacks:[item]}}}` (record = one planned *day*; the newer edit replaces the whole day, and clearing a day counts as an edit so it beats older content); `shopping: {checks:{itemKey:{on,updatedAt}}, extras:{id:{text,on,updatedAt}}}`. **Why one record per planned day, not per slot:** a day is small, edited by one person at a time, and whole-day replacement keeps merge trivial and provably convergent (property-tested); the cost is that two devices editing *different slots of the same day* offline will keep only the newer device's day. Acceptable for one user; the alternative (per-item records) can be adopted later without changing the UI. **Why the shopping *list* itself is not stored:** it is derived from the plan + recipes (so it can never go stale); only what the user does to it (ticking items, adding extras) is saved. **Sanitising:** recipe/plan/shopping data arrives from backups and from the cloud, so it is forced to safe types and capped in size (200 ingredients, 100 steps…) on every load, restore and sync (`sanitizeRecipe/PlanDay/Shopping`).

## D14. Recipe nutrition: "incomplete" is reported, never hidden — *made without the owner*
A recipe's calories are the sum of its **linked and convertible** ingredients; the UI shows "N of M linked" with the missing names and an *incomplete* badge (also on plan days that contain such a recipe). **Why:** silently counting an unknown ingredient as 0 kcal makes the numbers look precise while being wrong, which is the worst failure for a calorie tracker. Water, salt, pepper, ice and "to taste"/pinch items are not counted as "missing" because linking them adds noise, not accuracy (`recipes.js#isIgnorable`). **Cups/spoons need a density:** `resolveGrams` only converts volume units when the linked food has a volume measure in its database record (or a measure the user saved); otherwise the UI asks for grams instead of guessing that everything weighs like water.

## D15. Logging a planned recipe to the diary — *made without the owner*
A planned recipe becomes ONE diary entry "N servings" whose grams are the recipe's real serving weight × servings (so weights/units in the diary stay meaningful), or "100 g per serving" when the weight is unknown. **Idempotent:** the plan item stores the `entryId` it created; logging again does nothing unless that diary entry was deleted. A recipe with *no* linked ingredients is not logged (nothing meaningful to record) and the UI says why; a partly linked recipe logs what is linked (flagged incomplete). **Alternative considered:** logging each ingredient as its own entry — rejected because it floods the diary and breaks "I ate 1 serving".

## D16. Shopping list aggregation is conservative — *made without the owner*
Same ingredient is summed only across compatible units (weight→g, volume→ml, counts per unit word); weight and volume of the same ingredient stay as separate lines. **Why:** a wrong merge in a shopping list (buying 1 cup when you need 500 g) is worse than two lines. Grouping ignores size words ("large eggs" = "eggs") and plurals; names shown are as written in the first recipe. Ticks are keyed by `range start | normalised name | unit family`: they survive quantity changes, but belong to ONE shopping trip (a reviewer found that ticking onions this week also ticked them next week when ticks were keyed by name alone). Old ticks from past weeks accumulate as tiny records until "Untick all"; a rename orphans a tick (harmless). Aisles come from a keyword table, most specific aisle first; unknown → *Other*.

## D17. Navigation: Diary | Plan | Recipes | Shop | More — *made without the owner*
Five bottom tabs fit a 360 px phone; Export and Settings moved under **More** (with a "‹ More" back button) rather than shrinking the bar. `showTab('export'|'settings')` still works and highlights *More*.

## D18. Sync is scheduled by any data event, and sync results refresh every screen
`diary:changed`, `recipes:changed` and `plan:changed` all schedule a debounced sync; applying received data emits all of them (with an `applying` guard so a sync cannot trigger another sync by itself).

## D19. The ingredient parser keeps MealPlannerPC's vocabulary but not all of its choices
Ported: unit aliases, synonyms, descriptors, packaging words (the `tokens.json` file — parsing vocabulary only, no credentials). Changed on purpose: preparation words go to a `prep` field instead of being thrown away (the planner shows them), sizes like "(14 oz)" are kept in `prep` and used to resolve canned goods, ranges ("2-3") use the upper bound so shopping lists don't come up short, and names are **not** singularised at parse time so food search still finds "tomatoes" (the shopping list singularises only for grouping).

## D20. Products missing from the databases are handled with your own foods, matched by barcode
Open Food Facts and USDA do not contain every product (e.g. some protein bars). Instead of a second online source, a failed barcode search offers "Create a custom food for <code>", and the barcode is stored on that custom food (`barcode`, 8-14 digits, validated in `sanitizeFood`). Later scans/searches of that code show your food first; a barcode needs a name, and saving never erases a different product that merely shares the name (`replacesCustom`). The new field has no `SCHEMA_VERSION` bump on purpose (it is optional); an older app version on another device would drop it when it re-saves, which is acceptable. Codes are compared ignoring leading zeros (`sameBarcode`) because a UPC-A is an EAN-13 with a leading 0 and cameras report either; codes with fewer than 6 significant digits never match. Custom foods already sync, so the barcode syncs too. UPC-E (what a camera returns for a 'short' UPC) is NOT expanded to UPC-A, so it will not match a UPC-A saved by typing. Not done: looking the barcode up in USDA's branded-food data (needs the user's API key and a different endpoint).

## D21. A vendored decoder (ZXing) is the one exception to "no dependencies", used only as a scanning fallback
`BarcodeDetector` exists only in Chrome on Android/Mac, so Firefox, iPhone and Windows Chrome/Edge had no scanner. `js/vendor/zxing.min.js` is `@zxing/library` 0.21.3, copied unchanged (the package.json declares MIT but the LICENSE file it ships is the Apache-2.0 text; both are permissive, the shipped text is in `vendor/licenses/`) from the npm package's `umd/index.min.js` (336 KB, no build step, no `npm install`). It is loaded by a `<script>` tag only when a scan starts on a browser without the native detector, so it costs nothing otherwise. "Copied unchanged" is my statement: I did not compare hashes against the registry tarball. It is in the precache list so scanning works offline. Only EAN-13/EAN-8/UPC-A/UPC-E are enabled. To update: download the new file over the old one, rerun `npm test`, bump `CACHE`. Alternative rejected: a CDN `<script>` (third-party code at runtime, breaks offline).

## D22. Label reading is split into engine (pending) and parser (built); the result only prefills a form
`js/domain/label-parse.js` turns OCR *text* of a nutrition-facts panel into serving size and per-serving calories/fat/carbs/protein. It is pure and engine-independent, so it works with browser OCR (Tesseract.js, ~8 MB of vendored files, free, offline after first use, weaker on curved wrappers) or a vision model behind a small server function (accurate, but needs a backend, a secret key and a per-photo cost). The owner chose browser OCR (D23). Safety rules that hold either way: values only prefill the editable custom-food form; calories that disagree with 4P+4C+9F, macros heavier than the serving, or missing fields produce visible warnings; OCR digit look-alikes (O/0, l/1, S/5) are repaired only inside numeric tokens; a value is left empty rather than guessed (e.g. "69" for "6g"); only the FIRST column is read; if the label prints "per 100 g" first, the values are taken as per 100 g, the serving is set to 100 g and a warning says so (EU/UK layout). "Fat"/"Carbohydrate" without "Total" are accepted at the start of a line.

## D23. Label photos are read by Tesseract.js in the browser (free, private, offline after first use)
Chosen by the owner over a vision-AI server function (more accurate, but needs a backend, a secret key and per-photo cost; revisit when store integrations bring a backend). `vendor/tesseract/` (outside `js/`, so not precached) holds the engine and English data (~11 MB in the repo, ~7 MB downloaded per device once, cached in `macro-diary-ocr-v1`, which survives normal `CACHE` bumps). Photos are decoded at reduced size (`resizeWidth` 1800; unverified on a real phone) and then greyscaled and contrast-stretched before OCR. Measured on a rendered label: calories/fat/carbs/protein were read correctly, but "(50g)" came back as "(509g)" or "(509)" at every scale and page-segmentation mode tried, so the parser flags 3-digit serving weights ending in 9 and leaves a serving with no "g" empty. The camera photo is never uploaded; results only prefill the Custom form (highlighted until edited) with warnings; nothing is saved until the user presses Continue.

## D24. Label photos: two buttons, camera and upload
A single file input shows different things on different devices, and someone with no saved photo wants the camera directly. So there are two hidden inputs: `capture="environment"` (opens the rear camera on Android; iOS honours it too) and a plain one (gallery/files). On a desktop browser `capture` is ignored, so both open the file picker. On iPhone the plain input already offers "Take Photo", so the two buttons overlap there; harmless. Both feed the same reader (D23), both buttons are disabled while a photo is read, and only the newest read may re-enable them.

## D25. Sync setup: a built-in default project (the owner's project, set 2026-11-10) and a setup link in the URL fragment
Typing a Project URL and key is too much for end users. `js/services/sync/defaults.js` holds `DEFAULT_SYNC = { url, anonKey }`; `effectiveConnection()` picks the user's own project if they set one (or flipped "Advanced: use my own project"), else the default, else none, so a valid default means the user only signs in. Both values are public by design (the browser always sees them; row-level security protects the data), but the file must never hold a secret or service_role key (a test enforces it). The owner supplied their project's public URL and publishable key and they are now the default, so a new user only signs in. Hosting other people's data is still a product decision (docs/VISION.md: privacy, free-tier limits, who can sign up); clearing both values in `defaults.js` turns the built-in project off and restores the old behaviour. A user's own project never falls back to the default.
The "Add another device" link is `<app url>#sync-setup=<base64url {"v":1,"url","key"}>`. It uses the fragment, not a query, because browsers never send the fragment to a server, so it stays out of server and proxy logs. It carries only the URL and key (a test checks that passwords, emails and sessions are never included, and that service_role/`sb_secret_` keys and non-https URLs are refused). On open, the hash is stripped with `history.replaceState`; a bad link is ignored; a device already signed in to a different project asks before switching (`planSetupLinkApply` decides apply / confirm / ignore, and applying also clears that device's old session and sync bookkeeping). When the device is on the built-in default, "Add another device" says to just sign in there instead of showing a link. QR code: not done (a QR needs an encoder and the project has no dependencies); the link can be shared by message or opened by typing/pasting, and a QR is a follow-up.
A link for the same URL but a different key counts as a different project (it is applied, or confirmed if signed in). The toast after a link also appears when the link equals the default project.

## D26. Favourite recipes: a `favorite` boolean on the recipe (schema v5), no separate record
A star is just another recipe field, so it rides in the existing `recipe:<id>` sync record and the existing last-writer-wins merge: `setFavorite()` in `domain/recipes.js` sets it and stamps `updatedAt`, which makes a star/unstar an ordinary edit (the newest stamp wins on every device; a later delete still wins via the tombstone rules). Alternatives rejected: a separate `favorites` list or record (a second thing to merge and to keep in step with deletions), and a per-device setting (the plan says stars follow the recipe; auto-fill will read them). `sanitizeRecipe` forces the value to a strict boolean (only `true` is true), so a hostile backup or sync row cannot put anything else in it. v4 -> v5 changes no stored data: a missing flag reads as false and `updatedAt` is not touched, so old backups and old devices keep working (an old device that edits a starred recipe will drop the flag from its copy of the record, and the newer stamp wins; acceptable while there is one app version in use). `setFavorite` on the same value still re-stamps (simplest rule; it can only matter if two devices press at the same moment). Editor: for a saved recipe the star applies immediately, like the card star, and Cancel does not undo it; Save copies the current stored value into the draft so a stale draft cannot overwrite a newer star; for a new recipe the flag is part of the draft until Save. The Favourites filter is a per-screen toggle (not saved) that narrows the search; ordering is unchanged (favourites are not sorted first).

## D27. Auto-fill a week: rule-based, seeded, preview-then-accept, never overwrites
`js/domain/autoplan.js`: `proposePlan(state, opts)` is pure and returns a preview; `applyProposal` writes it through `plan.js addPlanItem` (so days are timestamped for sync) only on Accept. No AI and no schema change. The owner had not answered which rules matter first (VISION question 5), so the order is the documented default: (1) fit the daily calorie goal, (2) no repeat within `noRepeatDays` (default 3, counted in real calendar days, existing plan included), (3) prefer favourites. Each slot's target is the day's remaining budget (goal minus what is already planned) shared by slot weights (Breakfast .25, Lunch .30, Dinner .35, Snacks .10, renormalised over the slots being filled); servings are the nearest half-serving in [0.5, 4]. A favourite counts as a near match if its error is within 10% of the target of the best fit, otherwise a clearly better recipe wins. Variety comes only from a seeded generator (Reroll = next seed), so the same inputs always give the same proposal and it is testable. Only empty slots are filled; recipes with no nutrition are never picked, incomplete ones only if asked (the UI does not ask, so they are never offered yet); if the goal is already used up the smallest portion of the lowest-kcal recipe is proposed with a note; if every recipe is blocked by the repeat rule the rule is relaxed with a note. Apply skips any slot filled in the meantime, so accepting twice adds nothing the second time. The preview explains each pick in plain text ("why"), escaped in the UI. Not done: a month range (backlog item 3), slot targets that adapt to what earlier slots picked, preferring complete recipes over incomplete ones, prep-time and pantry rules. Also: if `state.goals.k` is itself invalid the goal falls back to 2000 kcal; when the goal is already used up the pick is the lowest-kcal recipe with a fixed tie-break (lowest id), so Reroll changes nothing in that case.

## D28. Plan month view: a read-only calendar that opens the week; auto-fill gets a Week/Month range and skips past days
The month view (`monthGrid`/`monthSummary` in `domain/plan.js`, Monday-first like the week) shows each day's planned kcal and item count and opens that day's week on tap; planning is still edited only in the week view, so there is one place that changes the plan. It does not add saved data or sync records. Padding days from neighbouring months are drawn empty and are not tappable. Auto-fill's range is chosen in its dialog (`autofillDates`): the week or calendar month containing the view, defaulting to the current view. Only today and later are filled; the dialog says how many past days were skipped (this resolves review finding 1 on PR #12, so a week that is partly in the past no longer gets meals planned for yesterday). The auto-fill rules (D27) are unchanged and simply run over more days, so the repeat window carries across weeks. The Plan tab's id generator now ends with a counter, so ids made within one millisecond (Accept can add dozens) cannot collide (review finding 2). The button still reads "Auto-fill week" in both views, which is slightly off in month view; kept so the existing label test does not change. A week that straddles two months (Mon Dec 29 - Sun Jan 4) opens the month of its Monday (December) when you switch to Month, and auto-fill's Month option from that week fills December; the dialog title also stays "Auto-fill week" in month view.

## D29. Recipe import: schema.org data or pasted text, one small fetch function, a private unsaved copy with a source link
**What.** Recipes tab -> Import. The user pastes a web address (only when the import service exists on their sync project) or pastes recipe text or a page's source. The result opens in the normal recipe editor as a NEW, UNSAVED recipe with a "Check before saving" list of warnings; nothing is saved until the user taps Save, and closing the editor asks before discarding. **Parsing** is pure and runs in the browser (`domain/recipe-import.js`): it reads schema.org `Recipe` JSON-LD (bare object, array, `@graph`, `@type` as a string or array, HowToStep/HowToSection) or pasted text (title, Serves/Total time, Ingredients, Method). Ingredient lines go through the existing parser (`newIngredient`), so nothing is linked to a food: the user does that, so **nutrition on the page is never imported** (honest numbers; a warning says it was ignored). *Reversed by D31: the page's per-serving numbers are now kept as the recipe's stated nutrition and always labelled as coming from the page.* **Fetching** is `supabase/functions/fetch-recipe` (a Supabase Edge Function, the one backend VISION section 5 proposed): it fetches one page and returns its text, stores nothing, has no keys of its own and keeps no logs of what was asked for. Its safety rules live in a plain file, `guard.js`, that Node tests import: http/https only, no credentials, ports 80/443, no private/loopback/link-local/reserved addresses in any spelling (decimal, hex, octal, IPv6, IPv4-mapped), redirects followed by hand with each hop re-checked, DNS answers re-checked (fails closed), 8 s limit, 2 MiB read limit (a longer page is cut, recipe data is near the top), only HTML/ld+json/text content types. The browser sends only the page address and the project's public key (`services/recipe-fetch.js`), never the diary or the sign-in session.
**Copyright and privacy (owner answers of 2026-11-10: yes to one small function, yes to "private copy with a source link").** An imported recipe is a normal recipe: it lives in the importing person's own browser and, if they sync, only in their own account (row-level security keeps other accounts out). The source link is kept; photos are never imported; nothing is republished. The ingredient list and quantities are facts, the written method and story are the part that can be protected, so the app keeps a personal copy, not a published one. Consequence for item 6 (households): sharing an imported recipe with other people would be republishing, so a household design should share only recipes people wrote themselves, or share an imported one as ingredients plus the source link. `source` only keeps a plain http(s) link (a `javascript:` or `data:` address becomes empty). No schema change: recipes already had `source`.
**Small choices.** Missing `totalTime` falls back to prep + cook when either exists. HowToSection names are dropped and the sections flattened (an open spec question; "For the sauce" context is lost). `parseYield` takes the first number ("2-3 servings" -> 2); bare numbers are never durations. Pasted text keeps lines before the first header as the description, so nothing typed is silently dropped. Entities are decoded once and tags removed; whatever is left is displayed through `esc()`. Page source pasted by hand is also accepted (View Source), which covers sites the function cannot fetch.
**Not done on purpose.** No URL import without the function (the app says so and offers paste), no scraping of sites without JSON-LD (old microdata-only blogs fall back to paste), no images, no auto-save, no background fetching.

## D30. Import dev tools: a local stand-in for the fetch function, and a local-only site corpus
**Stand-in.** `scripts/lib/fetch-recipe-core.mjs` implements the fetch-recipe contract in Node (same `guard.js`, manual redirects re-checked per hop, size/time limits, fixed outgoing headers) with the network and DNS injected, so it is unit-tested with fakes. `scripts/mock-supabase.mjs` (the existing dev-only sync mock) now serves `POST /functions/v1/fetch-recipe` with it, on `127.0.0.1` only. Point Settings -> Sync at `http://localhost:54321` (any 20+ character key) and Import by web address works without deploying anything. It is NOT the real runtime (Node DNS instead of Deno's, no platform limits, no CORS or key checks), so it does not replace the first real test after deploying (KNOWN-ISSUES 42). Known differences from `index.ts`: a refused private host or redirect answers HTTP 403 (the real function answers 200 with `ok:false`; the app reads the `ok:false` body first, so users see the same message), the core answers 405 to OPTIONS (the mock server handles the preflight before it gets there), DNS comes from the OS resolver, and the body must be an object with its own `url`. The mock now binds `127.0.0.1` only (it used to bind every interface), so a phone on the same network can no longer reach it; and it has no authentication, so any web page open in your browser could make it fetch a public page. It cannot reach private addresses and returns only public pages, which is acceptable for a development tool: run it only while you are testing.
**Corpus.** Real recipe sites have quirks. `npm run sites:add -- <url> [name]` saves the page's schema.org Recipe data plus the parser's result into `tests/local-sites/`, which is git-ignored: **third-party recipe text is never committed** (owner decision, 2026-11-10). The expected file is for human review (fix the parser, not just the file); `npm run test:sites` re-runs every saved site and exits 1 on any difference. It is separate from `npm test` and CI because the snapshots exist only on the machine that made them. A quirk found on a real site is pinned in the committed suite with an invented recipe (`tests/fixtures/site-corpus/`), never with the site's own text. File names always come from `siteSlug`/`slugPart`, never straight from what was typed, and an existing snapshot is only replaced with `--force`.
**First finds (a real page).** `recipeCategory`/`recipeCuisine` strings are now split on commas like keywords ("Dinner, Meal Prep" is two tags), and a recipeIngredient line that ends with a colon and has no digit ("Optional Toppings:", "For the sauce:") is a group label and is dropped (it also drops a lone "salt:", accepted). Lines that follow such a label (for example one line listing several toppings) are split into separate ingredients when they have no digit and at least 3 comma parts (commas inside brackets do not count): "sour cream, salsa, olives, lime wedges, shredded lettuce" becomes five lines so each can be linked to a food. The rule runs from a label until the next line with a digit or the next label, never applies to lines that do not follow a label, and never splits "salt, plus more to taste" or "salt, pepper" (fewer than 3 parts). It applies to the page route and the pasted-text route. A split part is not de-duplicated, and a line like "Dressing, 2 parts:" (a digit) is not a label.

## D31. Stated nutrition: keep the page's per-serving numbers, use them until every ingredient is linked, and work servings out from the serving size
**Why.** D29 imported no nutrition, so a new import showed 0 kcal until every ingredient was linked to a food, which made imports unusable for planning and logging. The owner decided (2026-11-10) to keep what the page says.
**What.** A recipe has an optional `stated` = `{ k, p, c, f, per }`: calories and grams of protein, carbs and fat PER SERVING, and the page's serving-size text (schema v6; `null` when there is none, `sanitizeStated` is the one validator: exactly those keys, numbers finite and in range, k <= 20000, p/c/f <= 5000). `recipeNutrition` gains `source` (`foods` | `stated` | `none`) and `estimated`: with a valid `stated` and not every ingredient linked, the per-serving numbers ARE the stated ones (`complete: true`, `estimated: true`, source `stated`); once every ingredient is linked the linked foods win (source `foods`). Plan totals, month view, auto-fill candidates, and "log to diary" all go through that, so a stated recipe plans and logs like any other (a logged stated recipe uses a 100 g "serving" for the entry's weight, as recipes of unknown weight already did). The importer reads the page's `nutrition` (calories like "336", "434 calories", "172 kcal"; kJ-only values are not used; macros like "31.8g", "80", "250 mg"); calories are required, a macro that is missing or unreadable counts as 0 and a warning names which ones; pasted text can carry `Calories:` / `Protein` / `Carbs` / `Fat` lines before the first section.
**Honesty.** The numbers are the site's claim, so they are labelled wherever they show: a "from page" badge on the recipe card, "Numbers are from the page (estimate)" in the editor, and an import note. The editor has four boxes (kcal, protein, carbs, fat) that work for any recipe, so the user can also type their own figures; blank kcal means none. Plan and diary totals include stated numbers without a separate per-total flag (KNOWN-ISSUES 45).
**Servings.** `servingsFromPage(recipeYield, servingSize)`: when the yield counts a thing ("12 Wings", "24 cookies") and the nutrition serving size counts the same thing, servings = yield / serving number ("12 Wings" per "12 Wings" is 1; "24 cookies" per "2 cookies" is 12); otherwise the old first-number rule (`parseYield`, unchanged), so "6 servings" with a "1.5 cups" serving size stays 6. Plural handling is simple (cookie/cookies, wing/Wings); irregular plurals (loaf/loaves) fall back to the old rule.
**Compatibility.** Schema v6 adds `stated` (migration: nothing to rewrite, sanitize defaults it to `null`). A device still on a v5 build drops the field if it edits such a recipe (like `favorite`, KNOWN-ISSUES 39). Sync records carry it inside the recipe value, so no database change.
