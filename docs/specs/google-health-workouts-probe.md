# Spec: Google Health probe, step 2: read the workouts (backlog item 24, step 1)

## Purpose
Before specifying "workouts from the Google Health API" (backlog item 24) the owner wants to see the REAL exercise answer: which fields Google sends for a workout (type, duration, calories, distance, heart rate, GPS) and how they are named. The existing developer probe (`tools/google-health-probe/`, spec `docs/specs/google-health-probe.md`) gets a third read, `Exercise`, whose result is mostly a STRUCTURE listing (field names and types, never values) that the owner can paste back safely.

Written before the implementation by the test designer. Where the request left a rule open this spec FIXES it ("decided here") so tests can pin it; the owner can change it before the build, and the implementer must then ask for the test to change, not edit it. Tests: `tests/google-health-workouts-probe.test.js` (B1-B18). Nothing in the shipped app, `sw.js` or the root `index.html` changes (no `CACHE` bump). No new scope: the exercise data type is under the scope the probe already requests, `googlehealth.activity_and_fitness.readonly`, and the probe still requests exactly the two existing scopes.

**What is known and what is not.** From Google's pages (unverified against a real answer): `GET https://health.googleapis.com/v4/users/me/dataTypes/exercise/dataPoints?page_size=25&filter=<url-encoded>` with filter `exercise.interval.civil_start_time >= "YYYY-MM-DD"`; a record has an `exercise` object with an `interval` shaped like sleep's, an activity type, `activeDuration`, `metricsSummary`, `hasGps`. THE EXACT FIELD NAMES ARE NOT KNOWN. That is why `describeShape` exists and why `summariseExercise` is best-effort until the real names are known: no helper may depend on a guessed field name other than `exercise` and `interval` (`startTime`, `startUtcOffset`, `endTime`, `endUtcOffset`, which are copied from sleep).

## Contract

Everything lives in `tools/google-health-probe/probe.js` (pure: no DOM, no network, no storage, no `console`). None of the three new functions throws, whatever the input (including throwing getters and Proxies).

- `buildExerciseUrl(now, days)` -> string. `https://health.googleapis.com/v4/users/me/dataTypes/exercise/dataPoints?page_size=25&filter=` + `encodeURIComponent('exercise.interval.civil_start_time >= "YYYY-MM-DD"')`, where the date is the first day of the same range as `buildSleepFilter` (now minus `days - 1` local days; `days` normalised exactly like the other builders: not a finite number -> 3, floor, clamp 1..31). `''` for an invalid `now`. Example, now 2026-11-14 20:00 local, days 3: `https://health.googleapis.com/v4/users/me/dataTypes/exercise/dataPoints?page_size=25&filter=exercise.interval.civil_start_time%20%3E%3D%20%222026-11-12%22`.
- `describeShape(json, opts = {})` -> string (see below).
- `summariseExercise(json)` -> `{ count, records: [{ type, localStart, localEnd, startDay }], text }` (see below).
- `resultSummary(results, showNumbers)` (existing) gains support for a check with a `shape` string (see below).

Exports of `probe.js` become exactly eleven functions: the existing eight plus `buildExerciseUrl`, `describeShape`, `summariseExercise`.

### `describeShape(json, opts = {})`
Returns the STRUCTURE of the first few data points as text, never values.
- Input: plain parsed JSON. Only an OWN property `dataPoints` that is an array is read (an inherited one, a `__proto__` key, a Map or a class instance gives the empty result). Items that are not plain objects (null, numbers, strings, arrays) are skipped first; then the first `N` objects are examined, where `N = opts.records`: not a finite number (including a string, `NaN`, `null`, a missing or non-object `opts`) -> 3; otherwise `Math.floor`, capped at 5 (minimum 1, decided here, see open question 5).
- Output: lines joined by `\n`, no trailing newline. ONE line per distinct path over all examined records (union), sorted by PATH with the default string comparison (UTF-16 code-unit order; a parent path sorts before its children). Every node gets a line, containers included, so `exercise: object` and `exercise.interval: object` are lines too (decided here, see open question 3). The record itself is the root and has no name: its keys are the first path segment. Line format: `<path>: <type>`.
- `<path>`: segments joined by `.`; array elements are collapsed to the segment `[]` appended to the array's path (`laps` is the array, `laps[]` its elements, `laps[].distance` a field of the elements); nested arrays give `[][]`.
- `<type>`: one of `string`, `number`, `boolean`, `object`, `array`, `null`. When the same path has different types (in different records or different array elements) ONE line lists them sorted alphabetically joined by `|` (for example `null|number`).
- Count: when a path does not occur in every examined record the line ends with ` (<k> of <n>)`, `k` = number of examined records the path occurs in (an array with many elements still counts once per record), `n` = number of records actually examined (not the number asked for). Paths that occur in all examined records have no suffix. Example with three records: `exercise.metricsSummary.pace: string (2 of 3)`.
- Enumerated values (the one allowed exception): a STRING value matching `^[A-Z][A-Z0-9_]{1,40}$` is printed as `<path>: string = RUNNING`. Every other value, whatever its type (numbers, booleans, times, ids, resource names, free text, lowercase or mixed-case text, empty string), is NEVER printed; only its type is. When a path holds different enum values across records, the format of that one line is not pinned (open question 4).
- Keys: a key is printed only if it matches `^[A-Za-z0-9_]{1,40}$` AND is not one of the three names `__proto__`, `constructor`, `prototype` (exact, case-sensitive; owner decision, they must never print as text); any other key (markup, spaces, empty, non-ASCII, longer than 40, or one of those three names) is replaced by `?`, and keys replaced by `?` that end at the same path are one path. The text of a key that is not safe never appears in the output.
- Depth limit 6: paths with more than 6 segments are not listed; a node at depth 6 still gets its own line, its children do not (`a.b.c.d.e.f: object` is listed, `a.b.c.d.e.f.g` is not). The record root is depth 0 and `[]` counts as a segment (open question 6).
- Line limit: at most 200 path lines; when more paths exist the first 200 in sorted order are kept and one final line `... more paths` is added (so 200 or 201 lines in total; the boundary reading is open question 7).
- Empty or garbage input (null, undefined, a string, a number, an array, `{}`, `dataPoints` missing, not an array or empty, only non-object items) -> the single line `no data points`.

### `summariseExercise(json)` (best-effort until the real field names are known)
- Reads an own `dataPoints` array of plain parsed JSON (same rules as `summariseSleep`): object items only, at most 25 examined, `count` = number examined.
- Each record `{ type, localStart, localEnd, startDay }`:
  - `localStart` / `localEnd`: decoded exactly like `summariseSleep`: `exercise.interval.startTime` / `endTime` (UTC strings `YYYY-MM-DDTHH:MM:SS[.fraction]Z`, real calendar date-times) plus `startUtcOffset` / `endUtcOffset` (`^-?\d+s$`, absolute value <= 86400) -> local civil time `YYYY-MM-DDTHH:MM:SS` (local = UTC + offset, fraction dropped, calendar rollover either way). Any bad or missing part -> `?` (never guessed as 0).
  - `startDay`: the local day the session STARTS on: the date part of `localStart`, or `?` when `localStart` is `?`.
  - `type`: the first string value that matches the enum shape `^[A-Z][A-Z0-9_]{1,40}$` among the top-level fields of `exercise` whose NAME contains `type` (case-insensitive), in the object's key order; otherwise `?`. A `type` field outside `exercise`, a field without `type` in its name, or a value of another shape (lowercase, markup, a number) does not count. Looking in nested objects is not decided (open question 8).
- `text`: one line per record joined by `; `, each line containing the type, `localStart` and `localEnd` in that order (the exact line format is not pinned, open question 9); `no exercise records` when there are none. `{ count: 0, records: [], text: 'no exercise records' }` for empty or garbage input.
- Hand-computed example: start `2026-11-14T23:30:00Z` with `3600s` -> `localStart` `2026-11-15T00:30:00`, `startDay` `2026-11-15` (the session starts on the NEXT local day); start `2026-11-15T00:10:00Z` with `-3600s` -> `2026-11-14T23:10:00`, `startDay` `2026-11-14`.

### `resultSummary` and `shape`
A check may carry `shape` (a string of lines). `resultSummary` then prints, directly in the summary: a line `<name> shape:` (the cleaned name, as for the verdict line) followed by the shape lines, EACH INDENTED BY TWO SPACES. This is printed ALWAYS (it holds no values), independent of `showNumbers`; `numbers` lines still print only when `showNumbers === true`. The block is contiguous. A `shape` that is not a non-empty string (undefined, null, numbers, objects, `''`, whitespace) adds nothing. Each shape line passes the same cleaning as other text (control characters become spaces, `ya29.` runs become `[token removed]`, email-shaped text becomes `[email removed]`), a shape line can never start a top-level line (every line of the block starts with two spaces). Everything else about `resultSummary` is unchanged, character for character. Where the block sits when other checks come AFTER the one that has it is open question 10 (the tests put `Exercise` last).

## Behaviours (tick list; tests B1-B18)
1. `buildExerciseUrl` gives the exact percent-encoded URL for the example; date = range start; `days` normalised like the other builders; `''` for an invalid `now`.
2. `describeShape` on a realistic workout record gives the exact sorted structure listing (golden, hand-computed).
3. `describeShape` never prints a personal value (names, ids, times, calories, distances, notes, tokens, emails, booleans' values) for realistic and hostile input.
4. `describeShape` unions paths over the first `records` objects (default 3, max 5, non-object items skipped first) and adds `(k of n)` only when a path is not in every examined record; `n` is the number actually examined.
5. `describeShape` sorts by path, collapses array elements to `[]` and lists different types of one path on one line.
6. `describeShape` prints enum constants (`^[A-Z][A-Z0-9_]{1,40}$`, exact length boundaries) as `string = VALUE` and no other string value.
7. `describeShape` shows only keys matching `^[A-Za-z0-9_]{1,40}$` except `__proto__`, `constructor` and `prototype`; every other key becomes `?` and never appears as text (exactly `?` for those three names); other prototype-looking keys (`toString`, `hasOwnProperty`, `valueOf`) print normally and do not break the listing; nothing pollutes `Object.prototype`.
8. `describeShape` depth limit 6 and the 200-line cap with the final `... more paths` line (first 200 in sorted order kept).
9. `describeShape` of empty/garbage input, inherited or `__proto__` `dataPoints`, non-plain objects: exactly `no data points`.
10. `describeShape` never throws and stays fast: throwing getters and Proxies, `records` options that throw, 1000 data points, 50000-level nesting, a 100,000-character string value.
11. `summariseExercise` decodes UTC time plus UTC offset to local time like `summariseSleep`, with `startDay` the local start day, including rollover either way, and the exact `{count, records, text}` shape.
12. `summariseExercise` finds `type` as specified and shows `?` otherwise.
13. `summariseExercise` of empty/garbage/hostile input (including bad offsets and times, throwing getters, 40 records) never throws; bad parts are `?`; at most 25.
14. `resultSummary` prints `<name> shape:` plus two-space-indented lines always; numbers still only when `showNumbers === true`; the old text is unchanged.
15. `resultSummary` ignores an unusable `shape`, cleans shape lines (tokens, emails, control characters), and a hostile shape cannot start a top-level line.
16. `probe.js` exports exactly the eleven functions (updated P18) and stays pure (no `document`, `window`, `fetch`, `console`, storage in code).
17. Source (WEAK): the page has `#check-exercise`, imports and calls the three new helpers, passes a `shape`, the probe builds the exercise endpoint with `exercise.interval.civil_start_time` and `page_size`, and no new scope appears; the page has `<label for="days">Days to read</label>` and `<select id="days">` with options 3 (default), 7, 14, 31, read in the click handler.
18. Docs (WEAK): the setup doc has the `Workouts check` section with the required content (choose `31` in `Days to read`); DECISIONS has the new entry.

## Edge cases and hostile input
- `now` invalid (`null`, `'x'`, `new Date(NaN)`, a number, `{}`); `days` `NaN`, `'3'`, `Infinity`, `-1`, `1e9`.
- JSON that is `null`, an array, a string, a number, `{}`; `dataPoints` not an array, an object, empty; items `null`, numbers, strings, arrays; `JSON.parse('{"__proto__":{"dataPoints":[{}]}}')` (an OWN `__proto__` key, not an inherited property); `Object.create({ dataPoints: [...] })`; a `Map`.
- Keys: markup (`<img src=x onerror=alert(1)>`), spaces, empty, 41 characters, non-ASCII, newlines; `constructor`, `toString`, `hasOwnProperty`, `valueOf`, `__proto__`.
- Values: HTML, `ya29.` token-like text, email addresses, phone numbers, a 100,000-character string, `NaN`-like numbers, numbers in the millions, resource names containing `/`, enum look-alikes (`Running`, `RUN-NING`, `1RUN`, `A`, 42 characters).
- Structure: 10-level and 50000-level nesting, arrays of arrays, empty arrays and objects, 500 keys in one record, 1000 data points, a getter that throws, a getter that returns something different on every read, Proxies whose traps throw. Circular objects cannot occur in parsed JSON; throwing getters can.
- Imported/synced data does not apply here (nothing is stored).
