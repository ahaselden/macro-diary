# Spec: Google Health sync (backlog item 20, step 2)

## Purpose
A "Sync Google Health" action pulls the last 7 local days of STEPS and SLEEP straight from the Google Health API (browser-only Google Identity Services token flow, no backend, no client secret; proven by the probe run on 2026-11-16) into the existing per-day `state.activity` records, so the dials and the activity line show them. Workouts are a later step and out of scope; no saved-shape change (no `SCHEMA_VERSION` bump: `state.activity` already exists, syncs and is in backups).

Written before the implementation by the test designer. Where the request left a rule open this spec FIXES it ("decided here") so tests can pin it; the owner can change it before the build, and the implementer must then ask for the test to be changed, not edit it. Tests: `tests/google-health-sync.test.js` (G1-G21 domain, S1-S10 service and client-id store, T1-T5 static source checks).

Documents to update in the same PR (the implementer, not the test designer): `docs/DECISIONS.md` gets `## D<next free number>. ### Domain (`js/domain/google-health-api.js`)
- `SYNC_DAYS` = `7`. Days to fetch: the last 7 local days including today (decided here: a week covers a few days of not syncing, one reconciled-sleep page of 25 records is normally enough, the steps roll-up allows up to 90 days so it is far inside the limit, and it keeps the answer small; older days stay with the zip import).
- `civilRange(now, days)`, `buildDailyRollUpBody(now, days)`, `buildSleepFilter(now, days)`, `buildSleepUrl(now, days, pageToken)`: same shapes and rules as the probe spec (`docs/specs/google-health-probe.md`, Date arithmetic), with these differences: `days` that is not a finite number defaults to `SYNC_DAYS` (7, the probe used 3); finite -> `Math.floor`, then clamped to 1..31. `buildSleepUrl` takes an optional third argument: when it is a non-empty string, `&pageToken=<encodeURIComponent(token)>` is appended after the filter; anything else is ignored. Invalid `now` (not a valid `Date`): `civilRange` and `buildDailyRollUpBody` give `null`, `buildSleepFilter` and `buildSleepUrl` give `''`. `now` is never mutated.
- `parseHealthAnswers(stepsJson, sleepJson)` -> plain object `{ 'YYYY-MM-DD': { steps?, sleepMinutes?, sleepStart?, sleepEnd? } }` keyed by LOCAL date. Either argument may be `null`/`undefined`/garbage (that part is then empty). Only days with at least one field appear; absent fields are absent (never `undefined`-valued). Never throws, never mutates its arguments, reads only own properties of plain objects/arrays.
- `applyHealthSync(state, days, now)` -> `{ added, updated, unchanged }`. `days` is a `parseHealthAnswers` result; `now` is a number of milliseconds. Mutates ONLY `state.activity` (creating it when something is written and it is missing).
- `healthSyncText(days)` -> the one-sentence result for the status line.
- `checkClientId(text)` -> `{ ok: true, id }` or `{ ok: false, message }`.

### Services (`js/services/google-health-api.js`)
- `GIS_URL` = `https://accounts.google.com/gsi/client`. `SCOPE` = `https://www.googleapis.com/auth/googlehealth.activity_and_fitness.readonly https://www.googleapis.com/auth/googlehealth.sleep.readonly` (exactly these two, one space between; no `openid`, no `email`).
- `CLIENT_ID_KEY` = `'macrodiary.googleclient.v1'`.
- `createClientIdStore(storage)` -> `{ get(), set(text), clear() }`. `storage` is injected (`localStorage` in the browser, a fake in tests, possibly `null` or throwing), like `createSyncConfig` in `services/sync/config.js`.
  - `get()` -> the saved Client ID, or `''` when none, when storage is null/throws, or when the stored text no longer passes `checkClientId` (a stored secret or junk is never returned).
  - `set(text)` -> `checkClientId(text)`; on failure `{ ok:false, message }` and NOTHING is written (the previously saved ID stays); on success writes the trimmed ID as the plain string under `CLIENT_ID_KEY` and returns `{ ok:true, id }`; when storage is null or `setItem` throws: `{ ok:false, message: 'Could not save the Client ID on this device.' }`.
  - `clear()` -> `get()` is `''` afterwards and no storage value equals the old ID (uses `removeItem` when available, else writes `''`). Never throws.
- `createHealthSync({ fetch, loadGoogle, now })` -> `{ run(clientId) }`. All three are injectable for tests; defaults: global `fetch`, a loader that adds a `<script src=GIS_URL>` once and resolves with `globalThis.google`, and `() => new Date()`. `run` returns a Promise and NEVER rejects:
  - success `{ ok: true, days }` (`days` = the `parseHealthAnswers` result);
  - failure `{ ok: false, message }`;
  - ignored tap `{ ok: false, busy: true, message: 'A sync is already running.' }`.
  Flow: (1) `checkClientId(clientId)`; invalid -> failure with that message, no `loadGoogle`, no `fetch`. (2) a run in progress -> the busy result, no second `loadGoogle`/`initTokenClient`/`requestAccessToken`/`fetch` (the busy flag is released when a run ends, success or failure). (3) `await loadGoogle()`; (4) `google.accounts.oauth2.initTokenClient({ client_id, scope: SCOPE, callback, error_callback })` then `.requestAccessToken()`; (5) a token response with a non-empty string `access_token` and no `error` continues; (6) steps: `POST https://health.googleapis.com/v4/users/me/dataTypes/steps/dataPoints:dailyRollUp`, header `Authorization: Bearer <token>`, `Content-Type: application/json`, body `JSON.stringify(buildDailyRollUpBody(now(), SYNC_DAYS))`; (7) sleep: `GET buildSleepUrl(now(), SYNC_DAYS)` with the same Authorization header, following `nextPageToken` (non-empty string) with `buildSleepUrl(now(), SYNC_DAYS, token)` for at most 4 pages in total (decided here: 100 records); (8) combine with `parseHealthAnswers`. ALL-OR-NOTHING (decided here): the first failure ends the run, later requests are not made, and no `days` are returned, so nothing is applied. Every request goes to `https://health.googleapis.com/v4/users/me/...` and to no other host. The token lives only in the closure of `run` (never stored, never in a URL or body, never in the result, a message, a status or a console call) and is dropped when `run` ends.

### Where the Client ID lives (decided here)
In its OWN `localStorage` key `macrodiary.googleclient.v1`, outside `state`, exactly like the per-device sync settings (`macrodiary.sync.v1`, D-sync config). Why not `state.apiKey` the D42 way: D42 keeps the USDA key out of sync records by an opt-in switch and a conditional field in `toRecords`, but `Backup to file` is `JSON.stringify(state)` and so DOES contain `apiKey` (KNOWN-ISSUES 56). A key outside `state` is in no sync record, no backup, no export, no merge and no `sanitize` by construction, so there is nothing to forget to filter. Each device enters its own ID. `STORAGE_KEY` is unchanged and `state` gains no field.

### Client ID rules (decided here)
`checkClientId(text)`:
1. not a string, or empty/whitespace-only after trimming -> `{ ok:false, message:'Enter a Client ID first.' }`.
2. contains `GOCSPX-` anywhere (case-insensitive), even inside a pasted JSON blob -> `{ ok:false, message:'That looks like a client secret, which must never be pasted here. Use the Client ID, which ends in .apps.googleusercontent.com.' }` (checked BEFORE the shape rule; the secret is never echoed, never stored).
3. otherwise the trimmed text must be `<prefix>.apps.googleusercontent.com` where `<prefix>` is 10 to 100 characters from `A-Za-z0-9_-` (no spaces, dots, slashes, control characters); else `{ ok:false, message:'That does not look like a Client ID. It should end in .apps.googleusercontent.com.' }`.
4. valid -> `{ ok:true, id }` with `id` the TRIMMED text.
No message ever contains any part of the input.

### Parsing rules (decided here, from the verified real answers)
Steps (`dailyRollUp`): `rollupDataPoints[]` items that are objects; the day = `civilStartTime.date {year, month, day}` (integers, a real calendar date, year 1000..9999; a string or any other shape is ignored); `steps.countSum` is a digit string `^\d{1,15}$` or a safe non-negative integer number, 0 to 200000 (the schema range; larger is ignored, never clamped); everything else (`'1e3'`, `'-5'`, `'12.5'`, `' 12'`, decimals, NaN, objects) is ignored. A missing `steps` object means no data: the day has no `steps` field. `"0"` is data: `steps: 0` (a worn day with no steps differs from no data). If two points name the same day the LARGER valid count is kept (decided here, deterministic whatever the order).

Sleep (`:reconcile`): `dataPoints[].sleep.interval {startTime, startUtcOffset, endTime, endUtcOffset}` and `sleep.summary.minutesAsleep`. A record counts only when: `startTime` and `endTime` are exactly `YYYY-MM-DDTHH:MM:SS[.fraction]Z` real date-times (the fraction is dropped, never rounded; the stored text is `YYYY-MM-DDTHH:MM:SSZ`), `endTime` is later than `startTime` and at most 24 hours later (as the zip import does), `endUtcOffset` is a duration `^-?\d+s$` with an absolute value of at most 86400 (e.g. `-18000s`, `3600s`, `0s`), and `minutesAsleep` is a digit string or a safe integer number from 1 to 1440. Anything else: that record is ignored, its siblings still count. `startUtcOffset` is not used (decided here: the start is stored as UTC text and only the END decides the day), see open question 4.
- The day a sleep belongs to is the LOCAL day it ENDS on: local end = `endTime` + `endUtcOffset`, taken in UTC arithmetic (so the machine timezone never matters), date part. This matches the zip import and the dials.
- Per day, `sleepMinutes` = the SUM of `minutesAsleep` of all records ending that day, capped at 1440 (as the zip import caps its total). Real example: the 16th had 159 and 239 minutes -> 398.
- `sleepStart` / `sleepEnd` = the UTC text of the MAIN record of that day: the record with the most `minutesAsleep`, ties to the one that ends later, then to the longer one. This is exactly the zip import's convention (`sleepByDay`: "the main sleep (most minutes, tie: ends later) gives the times"). The request suggested earliest start and latest end; that would not match the zip import (a nap in the early morning plus a later main sleep would produce one long made-up period), so this spec follows the zip import; see open question 1.
- Records need not be in any order (the answer is usually newest first); the result is the same in every order.

### Apply rules (`applyHealthSync`, decided here)
For each `day` of `days` (own keys; `isDateKey(day)` true; the value a plain object):
- Candidate fields: `steps` counts only when it is a number, whole, 0 to 200000; sleep counts only when `sleepMinutes` is a whole number 1 to 1440 (then `sleepStart`/`sleepEnd` count only as a valid pair in `sanitizeActivityDay`'s sense: both exact `YYYY-MM-DDTHH:MM:SSZ`, end later than start). Nothing else in the fields is read: a `workouts`, `source`, `updatedAt` or unknown key in `days` is ignored. A day with no counting field is skipped entirely (not counted, nothing written, no record created).
- New record = the stored record for that day (cleaned with `sanitizeActivityDay`; none if absent or unusable) with: `steps` replaced by the API value when it counts, else the stored `steps` kept (a day with no steps data keeps its steps; it is NOT zeroed); the sleep trio (`sleepMinutes`, `sleepStart`, `sleepEnd`) replaced TOGETHER by the API's when sleep counts (the old start/end are dropped even if the new pair is invalid, so minutes and times never mix), else the stored trio kept; the stored `workouts` ALWAYS kept as they are (the zip import replaces a whole day; this must not erase imported workouts); `source` = `'google-health'`; `updatedAt` = `now`.
- If the new record equals the stored one IGNORING `updatedAt` (and key order), nothing is written: `state.activity[day]` stays the same object with the same `updatedAt`, so sync pushes nothing; `unchanged` is incremented. Otherwise the record is written (`added` when there was no own key, else `updated`).
- DECISION (flagged for the owner): when the API step total differs from a stored one, EVEN a lower one for a past day or one that came from the larger-source zip rule, THE API REPLACES. Justification: it is the same watch, the API is fresher and is Google's own reconciled number (what the Google Health app shows), the zip import's "larger source" rule exists to avoid double counting phone and watch inside one export and the API roll-up is already reconciled, and a stored total from an older export of a partly finished day is partial, so "keep the larger" would freeze a stale number. A partial total from today that later grows is replaced by the larger one by the same rule. Re-importing a zip afterwards replaces the whole day again (D54), which is the owner's explicit action. See open question 2 (API `0`).
- Never throws: `now` not a finite number above 0, `state` or `days` not a plain object -> `{ added:0, updated:0, unchanged:0 }` and nothing changes. Keys that are not real calendar dates (`'2026-02-30'`, `'__proto__'`, `'constructor'`, `''`) are ignored; `Object.prototype` is never polluted. Every record written is a fixed point of `sanitizeActivityDay`. `days` is never mutated (frozen input is fine); nothing in `state` except `state.activity` changes.

### `healthSyncText(days)` (decided here)
Let `n` = days with `steps` or sleep (`sleepMinutes`), `s` = days with `steps` (a number), `l` = days with `sleepMinutes` (a number). `n > 0` -> `Synced <n> day(s): steps for <s>, sleep for <l>` (`1 day`, otherwise `days`; no trailing full stop), e.g. `Synced 3 days: steps for 3, sleep for 3`, `Synced 1 day: steps for 1, sleep for 0`. `n = 0`, or garbage -> `Nothing to sync: Google Health has no steps or sleep for the last 7 days.` Counts days returned by Google, whether or not they changed anything.

## Behaviours (tick list; tests carry the number)
Domain (pure)
1. (G1) `civilRange`/`buildDailyRollUpBody` give local start (days-1 back) and exclusive end (tomorrow) at 00:00:00 as CivilDateTime objects; `SYNC_DAYS` is 7 and is the default.
2. (G2) `civilRange` crosses month, year and leap-day boundaries, ignores the time of day, normalises `days` (default 7, floor, clamp 1..31); invalid `now` -> `null`; `now` is not mutated.
3. (G3) `buildDailyRollUpBody` = `{ range, windowSizeDays: 1 }` exactly; `null` for invalid `now`.
4. (G4) `buildSleepFilter`/`buildSleepUrl`: quoted `civil_end_time >=` filter on the range start, `page_size=25`, percent-encoded; optional `pageToken`; `''` for invalid `now`.
5. (G5) Steps from the real answer shape: 2026-11-14 12921, 2026-11-15 2919, 2026-11-16 1226.
6. (G6) Steps values: missing `steps` object = no day; `"0"` = 0; string and number counts; 200000 kept, 200001 and huge ignored; non-digit strings ignored.
7. (G7) Steps dates and shapes: impossible dates, strings, non-integers ignored; duplicate days keep the larger; empty and garbage answers give `{}`.
8. (G8) Sleep golden: several records on one day are added (16th: 159 + 239 = 398), main record gives start/end, order does not matter.
9. (G9) Sleep day = local END day: crossing midnight, negative, positive and zero offsets, end offset (not start offset) decides, exactly local midnight belongs to the new day, start stays UTC text.
10. (G10) Sleep records that are invalid are ignored one by one (bad times, offsets, minutes, end not after start, longer than 24 h); fractions of a second dropped; a day's total is capped at 1440; tie rule for the main record.
11. (G11) Steps and sleep merge per day; a day with only one side keeps only that side; days from either side appear.
12. (G12) Hostile answers (null, strings, arrays, wrong types, `__proto__` keys, throwing getters, 50,000 junk items) never throw, give `{}`, never mutate their input.
13. (G13) `applyHealthSync` adds a new day: record shape, `source`, `updatedAt = now`, counts.
14. (G14) Merge: workouts kept, steps and the sleep trio replaced independently, a day without steps keeps its steps, new minutes with bad times drop the old times.
15. (G15) The API replaces a lower or higher stored step total (zip, partial today).
16. (G16) Idempotent: applying the same days twice writes nothing the second time (object identity and `updatedAt` kept, counts `unchanged`); a changed value bumps `updatedAt`; identical content with an older stamp stays as is.
17. (G17) `applyHealthSync` ignores everything but steps/sleep in `days` (no workouts, source, updatedAt smuggled in); garbage fields write nothing and do not create `state.activity`.
18. (G18) `applyHealthSync` hostile input: bad `now`, bad `state`, bad `days`, non-date and prototype keys; records are fixed points of `sanitizeActivityDay`; frozen `days` fine; nothing else in `state` changes.
19. (G19) `healthSyncText` exact sentences.
20. (G20) `checkClientId` accepts real-looking IDs, trims, length bounds 10 to 100.
21. (G21) `checkClientId` rejects empties, wrong types, secrets (anywhere in the text), bad shapes; exact messages; never echoes the input.
Service and client-id store (fakes)

23. (S2) The Client ID never reaches state, sync records, a backup (`JSON.stringify(state)`), or the sync result; `state` gains no top-level key.
24. (S3) No Client ID (empty, secret, bad shape) -> no script load, no `initTokenClient`, no `fetch`; the exact message.
25. (S4) Success flow: `initTokenClient` gets the client id, the exact `SCOPE`, `callback` and `error_callback`; exactly the two requests (POST steps with the exact 7-day body, GET sleep with the exact URL), both with `Authorization: Bearer <token>`, only `https://health.googleapis.com/v4/users/me/` URLs; the result `days` is the golden.

27. (S6) Each token-flow failure gives its exact message and makes no Google Health request.

31. (S10) Edge: a 200 with `{}`/`null` answers is a successful empty sync; a token callback fired twice, or after an error, is harmless.

## Edge cases and hostile input
- Steps: no `steps` object, `countSum` as string and number, `'0'`, `'99999999999999999999'`, `'200001'`, `'1e3'`, `'-5'`, `'12.5'`, `' 12'`, `NaN`, `civilStartTime` missing/string/with month 13, day 0, 2026-02-30, float years; duplicates; `rollupDataPoints` not an array; items `null`.
- Sleep: several records per day, newest-first order, sleep crossing midnight, non-zero and different start/end offsets (DST day), offset forms `4h`, `1.5s`, `90000s`, missing; times with fractions, with `+01:00`, with a space instead of `T`, impossible dates; `minutesAsleep` `'0'`, `'1441'`, `'abc'`, `'-5'`, `'12.5'`, `''`, number 435; end before/equal start; period over 24 h; total over 1440.
- State: no `activity`, `activity` not an object, a stored record that is unusable, stored record with workouts, with a different key order, with an older `updatedAt`, frozen `days`.
- Client ID: empty, spaces, wrong types, secret in several spellings and inside JSON, `<img onerror>`, a URL, a 500-character text, a newline inside, prefix length 9/10/100/101.
- Errors: messages and bodies containing `ya29.` tokens, emails, HTML; `error` codes that are hostile (`ya29.x`, uppercase, 60 characters).
- Concurrency: a tap while pending, a tap after failure, a token callback that fires twice.

## What cannot be tested automatically

Nothing here can be proven headless: the unit tests use fakes for `fetch` and `google`, and the headless run stubs Google completely.

## Open questions
1. **sleepStart / sleepEnd.** The request suggested "earliest start and latest end". This spec uses the main record's times (most minutes asleep; tie: ends later), because that is what the zip import does (`sleepByDay`) and a re-import or a sync should write the same fields. Owner to confirm; if "earliest start and latest end" is wanted, test G8/G10 change.
2. **API says `0` steps for a day with stored steps.** By the "API replaces" rule `0` replaces a positive stored total. A watch not worn all day would give `"0"` or no point; the rule is simple but it can erase a zip total. Confirm, or decide that `0` never replaces a positive value.
3. **Two roll-up points for the same day** (should not happen with `windowSizeDays: 1`): the larger count is kept. Not verified against Google.
4. **`startUtcOffset`** is not required (only the end decides the day), so a record with a missing or bad start offset still counts. Confirm.
5. **No timeout** while the Google popup is open: if the user ignores it and Google never calls back, the buttons stay disabled until reload (the real popup normally reports `popup_closed`). A timeout was not specified.
6. **"Delete all data"** wipes `state` and does not touch `macrodiary.googleclient.v1` (the Client ID is a device setting, not diary data, like the sync settings). Not tested; confirm.
7. **All-or-nothing** (steps worked, sleep failed -> nothing is applied). The alternative is to apply the half that worked and show a warning; chosen here for a simple honest status line.
8. **`pageToken` / `nextPageToken`** names are taken from the probe spec (verified against Google's pages there); the owner's real run returned a single page.
9. A far-future or far-past day in Google's answer is applied as long as it is a real date (no range check against today).
