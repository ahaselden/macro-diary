# Spec: Google Health sync reads workouts (backlog item 24, step 2; builds on `google-health-sync.md`, `google-health-seamless.md`, `google-health-workouts-probe.md`)

## Purpose
The Google Health sync (Settings button, Diary button, quiet sync on open) also reads the last 7 days of EXERCISE sessions with the same sign-in and the same permission (`activity_and_fitness.readonly`: no new scope, no new consent) and merges them into `state.activity[day].workouts`; the Diary's day details show each workout with distance and average heart rate (distance follows the units setting). A failed workouts request never costs the steps and sleep that were read.

Written before the implementation by the test designer. Where the request left a rule open this spec FIXES it under "Decided here" so tests can pin it; the owner can change it before the build, and the implementer must then ask for the test to change, not edit it. Tests: `tests/google-health-workouts.test.js` (X1-X14 pure domain, V1-V4 the Diary line, Y1-Y9 the service with fakes, Z1-Z3 round trip and WEAK source-text checks). Values in tests are made up; the field layout is the owner's real probe run (values omitted).

## Contract

### `js/domain/google-health-api.js` (pure; no DOM, no network, no storage, no clock)
- `buildExerciseFilter(now, days) -> string`: `exercise.interval.civil_start_time >= "YYYY-MM-DD"`, the date being the first local day of the window (same rule as `buildSleepFilter`: `days` normalised like the other builders, default `SYNC_DAYS` = 7); `''` for an invalid `now`.
- `buildExerciseUrl(now, days, pageToken) -> string`: `https://health.googleapis.com/v4/users/me/dataTypes/exercise/dataPoints?page_size=25&filter=` + `encodeURIComponent(filter)`, plus `&pageToken=` + `encodeURIComponent(token)` for a non-empty string token; `''` for an invalid `now`. Example for 2026-11-16 12:00 local, 7 days: `.../dataTypes/exercise/dataPoints?page_size=25&filter=exercise.interval.civil_start_time%20%3E%3D%20%222026-11-10%22` (identical to the probe's URL).
- `parseExerciseAnswer(json) -> { 'YYYY-MM-DD': Workout[] }` keyed by the LOCAL day each session STARTS on. Never throws, never mutates. `Workout` is exactly the saved shape `{ id, name, start, minutes, kcal?, steps?, distanceM?, avgHr? }` (no `peakHr`: not available from the API).
- `parseHealthAnswers(stepsJson, sleepJson, exerciseJson)`: a THIRD, optional argument. When it yields workouts for a day the day gets `workouts: Workout[]` (a day with only workouts appears). With the third argument missing, `null` or junk the result is exactly what the two-argument call returns today.
- `applyHealthSync(state, days, now)` (extended): see "Merge rule".
- `healthSyncText(days, workoutsError)` (extended second argument) and `WORKOUTS_FAILED_TEXT` (exported constant): see "Texts".
- Existing exports keep working unchanged: `SYNC_DAYS`, `civilRange`, `buildDailyRollUpBody`, `buildSleepFilter`, `buildSleepUrl`, `checkClientId`, `shouldAutoSync`, `syncAgoText`.

### `js/domain/activity.js`
- `workoutLine(w, weightUnit) -> string`: the plain-TEXT line of one stored workout for the Diary details (see "The Diary line"). Never throws. Existing exports unchanged.

### `js/services/google-health-api.js`
- `createHealthSync(...).run(clientId, opts)` reads the exercise endpoint as a THIRD request (after steps and sleep, GET, `buildExerciseUrl(today, SYNC_DAYS, token)`, same bearer token, same paging rule: follow `nextPageToken`, at most 4 pages, a missing / empty / non-string token ends paging). Result: `{ ok: true, days }` when the exercise request worked (including an empty answer), `{ ok: true, days, workoutsError: WORKOUTS_FAILED_TEXT }` when it failed. Sign-in, steps and sleep failures stay ALL-OR-NOTHING exactly as today (`{ ok: false, message }`, no `days`, and the exercise request is not made). Existing exports and messages unchanged; `SCOPE` unchanged.

### `js/ui/diary.js`, `js/ui/health-sync-view.js`
- `diary.js`: the Workouts list in the day details draws `esc(workoutLine(w, state.weightUnit))` per workout (the heading text `Workouts` stays).
- `health-sync-view.js`: the status / toast text is `healthSyncText(res.days, res.workoutsError)`; nothing else new.

### Saved shape: NO change
`state.activity[day].workouts` already exists (D54; `sanitizeWorkout` / `sanitizeActivityDay` in `core/schema.js`: max 20 a day, ids 1..80, name <= 60 plain text, `minutes` 0..1440, `kcal` 0..20000, `steps` 0..200000, `distanceM` 0..1,000,000, `avgHr` and `peakHr` 20..300). No `SCHEMA_VERSION` bump (stays 13), `STORAGE_KEY` unchanged, no migration, no change to sync records (`activity:YYYY-MM-DD` already carries the day), backup or merge. Records written by the sync carry `source: 'google-health'` as for steps and sleep. No new shipped file, so `sw.js` SHELL needs no entry (CACHE must still be bumped because shipped files change).

## Decided here

**Field mapping** (one data point -> one workout; the real field layout is in the probe spec):
- `id`: the last `/`-separated segment of `name` (`users/me/dataTypes/exercise/dataPoints/<id>` -> `<id>`). A record whose `name` is missing or not a string (or has an empty last segment) gets a DERIVED id: deterministic (the same record always gives the same id), 1..80 characters, different for a different start time. The format is not pinned. An id longer than 80 characters must never produce an invalid workout (skipped or made valid; open question 2).
- `name`: `exercise.displayName` when it is a string that, after removing control characters (`\u0000-\u001f`, `\u007f-\u009f`) and trimming, is non-empty; cut at 60 characters; markup is kept as TEXT (escaping happens when drawn). Otherwise a label from `exercise.exerciseType` when it matches `^[A-Z][A-Z0-9_]*$` (at most 60 characters): first letter upper case, the rest lower case, `_` becomes a space (`RUNNING` -> `Running`, `HIGH_INTENSITY_X` -> `High intensity x`, `OUTDOOR_BIKE_RIDE` -> `Outdoor bike ride`). Otherwise `Workout`.
- `start`: `exercise.interval.startTime` as UTC text `YYYY-MM-DDTHH:MM:SSZ` (a fraction of a second is dropped, never rounded). The accepted input forms are those of the sleep parser (`...Z` with an optional fraction; `+01:00` forms are refused). A record with an unusable start is skipped. A missing or unusable `startUtcOffset` (must match `^-?\d+s$`, absolute value <= 86400) also skips the record: the local day cannot be known and is never guessed as UTC (same rule as sleep, open question 3).
- Local day: `start` + `startUtcOffset`, in UTC arithmetic (the machine's timezone never matters). The START offset decides, not the end offset. A session starting at exactly local 00:00:00 belongs to the new day; one second earlier to the previous day.
- `minutes`: `exercise.activeDuration` when it is a string `<digits>[.<digits>]s` (a protobuf Duration; the real format is UNVERIFIED, so anything else counts as unusable), converted to minutes and rounded to the nearest minute with .5 rounding up (`1590s` = 26.5 -> 27, `1569s` = 26.15 -> 26, `1585.5s` -> 26); a duration above 1440 minutes (86400 s) is unusable (never clamped). When the duration is unusable or absent: the interval length (`endTime` - `startTime`, same rounding) when `endTime` is a usable time not before the start. When neither is usable: `0` and the workout is kept (open question 4). `endUtcOffset` is not needed.
- `kcal` = round(`metricsSummary.caloriesKcal`), `distanceM` = round(`distanceMillimeters` / 1000), `steps` = `steps`, `avgHr` = `averageHeartRateBeatsPerMinute`. Numbers and digit strings are both accepted for all four (`caloriesKcal: 312.4` and `"312"`; `steps: 5120` and `"5120"`). Out-of-range values (kcal outside 0..20000, distance outside 0..1,000,000 m, steps outside 0..200000, heart rate outside 20..300) are DROPPED, never clamped; NaN, Infinity, negatives, text, booleans, objects are dropped. A missing metric (or a missing / non-object `metricsSummary`) is an absent key, never 0; an explicit `0` kcal / steps is data. Metric names are read from OWN properties only.
- Never copied: `peakHr`, pace, elevation, zones, splits, events, GPS flag, device, any other field.
- Per day: sorted by `start`, then `id` (string comparison); one id is one workout (a repeat, on the same or another claimed day, is dropped; which copy is kept is not pinned); two sessions starting in the same minute (even second) are both kept; at most 20 per day, the EARLIEST kept (whatever the order of the answer).

**Merge rule (`applyHealthSync`).** For each day in `days`: when the day's `workouts` (a plain array) has at least one workout that survives `sanitizeActivityDay`, the stored day's workouts are REPLACED wholesale by those (so a Takeout-zip workout, with its `peakHr`, is gone and nothing is shown twice; at most 20, in the order given). Otherwise (missing, not an array, empty, nothing valid) the stored workouts are kept. Days not in `days` are untouched. Steps and the sleep trio keep their independent per-field rules (a field absent from `days` keeps its stored value). A day with only workouts is written (it needs no steps or sleep). A record equal to the stored one ignoring `updatedAt` writes nothing and counts as `unchanged` (the stamp is not bumped, the stored object is not replaced). Every record written is a fixed point of `sanitizeActivityDay` and holds copies of the workouts (never the answer's objects). `now` / `state` / `days` validity rules and the `{ added, updated, unchanged }` return are as today. The old rule "workouts in `days` are ignored" is gone (it changes `G17` of `tests/google-health-sync.test.js`, see below).

**Texts (`healthSyncText(days, workoutsError)`).**
- Without workouts and without `workoutsError` the text is byte for byte today's: `Synced N day(s): steps for S, sleep for L` / `Nothing to sync: Google Health has no steps or sleep for the last 7 days.`
- A day counts as synced when it has steps, sleep or workouts (a non-empty `workouts` array). When at least one day has workouts, `, workouts for K` is appended, `K` = the number of DAYS with workouts (not the number of workouts): `Synced 3 days: steps for 3, sleep for 3, workouts for 2`; workouts only: `Synced 1 day: steps for 0, sleep for 0, workouts for 1`. An empty list or a non-array counts as no workouts. With no workouts at all the `, workouts for` part is not there (so a stored-workouts-only history never changes the old sentences).
- `WORKOUTS_FAILED_TEXT = 'Workouts could not be read from Google Health.'`. When `workoutsError` is truthy it is appended after the base text and a full stop: `Synced 3 days: steps for 3, sleep for 3. Workouts could not be read from Google Health.`; after the nothing-to-sync sentence (which already ends with a full stop) with a single space: `Nothing to sync: Google Health has no steps or sleep for the last 7 days. Workouts could not be read from Google Health.` The value of `workoutsError` is a flag: its text is never shown (a hostile string is not echoed).

**Failure rule (service).** Any failure of the exercise request (non-2xx status including 401/403/429 and ACCOUNT_NOT_LINKED, network error, an unreadable body) at ANY of its pages makes `workoutsError` the one fixed text and drops ALL exercise data of the run (no half result from earlier pages); steps and sleep are returned and applied. No cause is given (one fixed message, nothing from Google is echoed, the token never appears). A quiet (silent) run behaves identically; its result carries no `silent` flag (that flag only marks failures before a token). The request is not retried. A `200` answer of `{}`, `null`, `[]`, an empty list or junk items is a SUCCESS with no workouts (no `workoutsError`). The key `workoutsError` is ABSENT, not `undefined`, on success.

**The Diary line (`workoutLine(w, weightUnit)`).** Plain text, parts joined by ` · `, in this order, parts that are not recorded left out:
1. the name (`Workout` when `name` is not a non-blank string);
2. `<minutes> min` ALWAYS (the existing behaviour; a missing, non-finite or out-of-range (outside 0..1440) `minutes` shows `0 min`);
3. distance when `distanceM` is a finite number in 0..1,000,000: `weightUnit === 'oz'` -> `distanceM / 1609.344` miles, anything else (`'g'`, `undefined`, junk) -> `distanceM / 1000` kilometres; one decimal always (`4200` -> `4.2 km`, `3000` -> `3.0 km`, `4200` oz -> `2.6 mi`), suffix ` km` / ` mi`;
4. `<kcal> kcal` when `kcal` is a finite number in 0..20000 (as before for valid data);
5. `avg <avgHr> bpm` when `avgHr` is a finite number in 20..300.
Example: `Running · 31 min · 4.2 km · 312 kcal · avg 148 bpm`. `peakHr` and `steps` are not shown. Only OWN properties are read. The result is TEXT, not HTML: `diary.js` applies `esc()` to the whole line. A value that is not a workout object gives `''`. Never throws; never prints `NaN`, `Infinity`, `undefined`, `null` or exponent text. Numbers outside the saved-shape ranges (which `sanitizeWorkout` never lets in) count as not recorded: the part is left out and minutes show `0 min` (decided here, open question 5).

## Edge cases and hostile input (covered by the tests above unless marked)
- Empty answer, 0 records, 25+ records on a day (cap 20, earliest), duplicate ids (also across pages), two sessions in the same minute, a start offset that moves the session to another local day, exactly local midnight, month / year / leap rollover, the clock-change case (start offset differs from end offset).
- Numbers as strings and strings as numbers; NaN, Infinity, negative, huge (1e15 mm, 1e9 kcal), `'1e2'`, `' 12'`, `''`, `{}`, `[]`, `true`.
- `__proto__` keys inside the answer, inside a record, inside `metricsSummary`, as a day key in `days`; inherited `dataPoints` / `exercise` / metric properties; getters that throw.
- displayName with markup, quotes, an ampersand, control characters, newline, 100 characters, only whitespace.
- Imported / synced data: workouts arriving in a sync record or a restored backup go through `sanitizeActivityDay` as before (existing tests); a stored zip workout (with `peakHr`) replaced by an API one (X12).
- Frozen inputs are neither mutated nor aliased (X10, X13).
- Not automated: a real clock-change day, a 31-day window, responses of several MB.

## Open questions
1. Is a `startUtcOffset` that is missing really a skip (decided here, as sleep does), or should a missing offset fall back to the user's current timezone? The tests pin the skip.
2. The request says "records with ... no id are skipped" AND "else a derived stable id". This spec lets a record with no usable `name` get a derived id (tests pin: kept, stable, valid, differs by start) and says nothing is skipped for lack of an id. An id over 80 characters is left to the implementation (skip or shorten), tests only require validity.
3. Should the parser / merge also drop days outside the 7-day window if a (stubbed) API returns older sessions? Neither does today; the filter bounds the answer. Not tested.
4. A session with no usable duration and no usable end is kept with `0 min` (the zip import does the same). The owner may prefer to skip it.
5. `workoutLine` treats numbers outside the saved-shape ranges as not recorded (they cannot occur after `sanitizeActivityDay`; decided so that no exponent text or absurd number can be drawn). An explicit `0 m` distance prints `0.0 km` and `0 kcal` prints `0 kcal` (not tested); the owner may prefer to hide a zero distance.
6. `workoutsError` is a flag for `healthSyncText` and ALSO the fixed text itself (`run` returns `workoutsError: WORKOUTS_FAILED_TEXT`). If the owner wants different messages per cause (403 vs network) that is a new decision; today one fixed message.
7. A day that the API lists with workouts but the user deleted the stored workouts for: replaced again at the next sync (the API is the truth for that day). Intended, not tested beyond X12.
8. Element ids for the checklist: the Diary details dialog is opened with `#dialsOpen` (existing) and its body is `#dBody` (as in the import scenario); the day is chosen with `#prev` / `#next`; the units select is `#wUnit` with values `g` / `oz`. If the details dialog changes, the checklist needs the new ids.
