# Ids for saved foods (fixes KNOWN-ISSUES 55)

Backlog "Later / unscheduled": ids for saved foods. Saved custom foods (`state.custom`) are matched across devices, in merges and for saved measures by `foodKey` (`name|brand|source`), so a rename on one device brings the old name back as a duplicate, two same-name foods with different barcodes cannot be edited, and measures of a renamed food are orphaned on the other device. This feature gives every saved food a stable `id`, merges and syncs by id, keys saved measures by that id, and migrates existing data without creating duplicates when two devices migrate independently.

Tests: `tests/saved-food-ids.test.js` (numbers match the behaviour list below). Existing tests that pinned schema 8 or key-based editing were edited; the list is at the end.

## Design decisions (made here, the implementer follows them)

**D-A. Two kinds of id, one shape check.** `isFoodId(v)` is true exactly for a string matching `/^f(?:-[0-9a-f]{16}|[0-9a-z]{6,24})$/`.
- *Generated* ids (new foods): `makeFoodId(now, rnd)` = `'f'` + `now.toString(36)` + a 4-character random part `Math.floor(rnd() * 36**4).toString(36).padStart(4, '0')`. Never contains `-`. (`rnd` and `now` are arguments so the function is pure; the UI passes `Date.now()` and `Math.random`.)
- *Derived* ids (legacy foods, i.e. every food that existed before this change or arrives from an old-app device without an id): `legacyFoodId(food)` = `'f-'` + 16 lowercase hex digits of the **64-bit FNV-1a hash** (offset basis `0xcbf29ce484222325`, prime `0x100000001b3`, byte XOR then multiply modulo 2^64, over the UTF-8 bytes) of the string `foodKey(food) + '|' + barcodePart`, where `barcodePart` is the food's barcode with leading zeros removed when it is a valid barcode (8 to 14 digits, `sameBarcode` equivalence), else `''`. So a food with no barcode hashes `name|brand|source|`.
- The algorithm is pinned (golden values in the tests) because two devices running different builds must derive the same id forever. It lives in `js/core/schema.js` (core may not import domain, so it recomputes `[name, brand, source].join('|')`; a test checks it agrees with `foodKey`).
- The barcode is part of the derivation so two foods with the same name/brand/source but different barcodes (allowed by `replacesCustom`) get different ids and neither is lost. Limitation, accepted: if one device edited a legacy food's barcode before both devices migrated, the two copies derive different ids and show up as a duplicate pair after the first sync (visible, nothing is lost; the owner can keep one).
- 64-bit collisions between different keys are not handled specially (probability negligible). Two foods in one list that derive the SAME id (same key and same barcode, a true duplicate) are collapsed: newest `updatedAt` wins, on a tie the larger `JSON.stringify` wins (the same tie rule as `mergeStates`), independent of list order.

**D-B. The id lives on the saved food as `id`; copies carry `foodId`.** A diary entry already has its own `id`, so copies of a saved food (diary entries, recent foods, recipe-ingredient foods, plan foods) carry the saved food's id as **`foodId`**. A copy is otherwise unchanged. `measuresKey(food)` (`js/domain/food.js`) is the one function that says where a food's saved measures live: valid `food.foodId`, else valid `food.id`, else `foodKey(food)`. An entry's own `id` is never a food id in practice (entry ids are time-ordered base 36 starting with `m` or `n` today, saved-food ids start with `f`), and anything that fails `isFoodId` is ignored.

**D-C. Measures.** For a saved food, `state.measures[food.id]`. For anything that is not saved (USDA, Open Food Facts, recents of those) `state.measures[foodKey]` as before. `unitsFor(food, measures)` reads `measures[measuresKey(food)]` only: when a food has an id, the foodKey bucket is NOT consulted. `resolveGrams` and `recipeNutrition` need no signature change (they call `unitsFor`), so recipes resolve by `ingredient.food.foodId` and fall back to the foodKey bucket when it is absent. A rename or brand change no longer moves measures.

**D-D. Migration to schema 9** (`migrate`, runs on load and on every restored or synced old-app payload through `sanitize`):
1. each saved food without a valid `id` gets `legacyFoodId(food)` (a valid existing id is kept; an invalid or hostile one is replaced by the derived id), duplicates collapsed per D-A, order preserved;
2. measures: for each saved food, `measures[foodKey(food)]` is merged into `measures[food.id]` (lists merged by label, the newer `updatedAt` wins, a missing one counts as 0; if two saved foods share the key both get the list), and the foodKey key is removed when it belonged to a saved food. Measures of foods that are not saved stay where they are;
3. existing copies get `foodId` (diary entries, `recent`, recipe-ingredient `food`, plan `food`) when they match exactly one saved food: same name, brand and source and either (copy has a barcode and it is `sameBarcode` as exactly one of the candidates) or (copy has no barcode and exactly one saved food has that key). Ambiguous or non-saved copies get nothing. Nothing else on the copy changes, `updatedAt` included, so migrating never makes an entry "newer".
4. `sanitize` keeps a `foodId` only when it passes `isFoodId` (also on sync records and backups) and gives every saved food a valid id.

`mergeStates` normalises BOTH sides first with the same rules (ids derived for foods without one; hostile ids replaced), so a v8 backup or an old-app sync record merges without duplicates. After matching it also folds measure buckets keyed by a saved food's `foodKey` (what an old-app device keeps writing) into that food's id bucket. Copies (`foodId`) are NOT stamped by merge; an entry or recipe food that arrives from an old-app device after the migration has no `foodId` and resolves measures by `foodKey`, which only finds non-saved foods. Accepted limit: such an entry opened in "Edit entry" does not offer the saved food's own measures until the entry is re-picked (its grams are unaffected).

**D-E. Merge by id.** `mergeStates` matches saved foods by `id` (not `foodKey`), the newest `updatedAt` wins **as a whole record** (so "A renamed at 2000, B changed the numbers of the old-named food at 3000" gives B's version: old name, new numbers; the rename is lost, which is the same last-writer-wins trade-off as for diary entries). Order is `updatedAt` descending, then `id` ascending; at most 100 foods are kept after sorting. Output foods are new objects when an id was added; inputs are never mutated.

**D-F. Deletion.** There is still no delete UI. Rules pinned so a future delete works and so that replacing a food never leaves a duplicate on another device:
- A tombstone `state.tombstones[foodId] = deletedAt` hides a saved food whose `updatedAt <= deletedAt` and does not hide one edited after it (the existing entry/recipe rule, one shared tombstone map). Food ids are in the same namespace as entry and recipe ids; the `f` prefix keeps generated ones apart in practice. A tombstone for a food id never affects an entry or recipe with a different id.
- `addCustomFood(state, food, now, makeId)` (new, `js/domain/food.js`): the new food REPLACES every saved food `f` with `replacesCustom(f, food)`. It inherits the id of the first replaced food (so its measures and other devices' copies follow), the ids of any further replaced foods get tombstones at `now`, and the saved food goes first with `updatedAt = now`. With nothing replaced it gets `makeId()`. Adding clears a tombstone for the id it uses. Cap: after inserting, the list is cut to 100 (oldest, i.e. last, dropped); **cap eviction does NOT create a tombstone** (a tombstone would delete the food on every device; the merge re-applies the same 100 cap deterministically). Measures of an evicted food stay in `state.measures` (open question 2).

**D-G. Editing by id.** `updateCustomFood(state, id, patch, now)`: the second argument is the food's `id` (not its key). Everything else about it is unchanged (spec `edit-quick-add.md`) except: it never moves measures; the id never changes; a `foodKey` string or anything that is not the id of a saved food returns `null`; two saved foods with the same name/brand/source and different barcodes can each be edited; the collision rule (`replacesCustom` against the OTHER saved foods) still refuses an edit that would make it the same product as another saved food.

## Contract

`js/core/schema.js`
- `SCHEMA_VERSION = 9`; `defaults().schemaVersion` is 9; `STORAGE_KEY` (`js/core/constants.js`) stays `macrodiary.v1`.
- `isFoodId(v) -> boolean` (D-A). Never throws.
- `legacyFoodId(food) -> string | null`: derived id (D-A) for a plain object (non-string name/brand/source count as `''`, a non-valid barcode as none); `null` for anything that is not a plain object. Pure, no mutation, never throws.
- `migrate(d)` has the v9 step (D-D); `sanitize(d)` gives saved foods valid unique ids and cleans `foodId` on entries, `recent`, recipe and plan foods.
- `sanitizeFood(f)` (recipe/plan foods): keeps `foodId` when valid; a valid `f.id` becomes `foodId` (a saved food object was linked directly); never outputs `id`.

`js/domain/food.js`
- `makeFoodId(now, rnd) -> string` (D-A). Never throws; always returns an `isFoodId` string (a non-finite `now` counts as 0, a bad `rnd` result as 0).
- `measuresKey(food) -> string` (D-B).
- `addCustomFood(state, food, now, makeId) -> food | null` (D-F). Mutates `state` (`custom`, `tombstones`). Returns `null`, state untouched, for unusable `state`/`food` (no name or no per100), non-finite `now`, a `makeId` that is not a function or returns something failing `isFoodId` (or an id already used by another saved food).
- `updateCustomFood(state, id, patch, now)` (D-G).

`js/domain/units.js`: `unitsFor(food, measures)` uses `measuresKey(food)`.
`js/domain/merge.js` (`mergeStates`), `js/domain/sync-records.js` (`toRecords`, `applyRecords`), `js/domain/backup.js` (`mergeRestore`): as D-D/D-E. The sync record keys and shapes do not change (`custom` holds foods that now carry `id`; `measures` is keyed by id for saved foods).

UI (wiring, no new visible text): `add-food.js`, `plan-view.js`, `recipe-editor.js` pass `foodId: f.id` on saved-food results; `custom-food.js` saves with `addCustomFood` and edits with `updateCustomFood(state, editing.id, ...)`; `amount-picker.js` reads and writes saved measures with `measuresKey(food)` and puts `foodId` on the entry and the recent food it creates when the food is a saved one.

## Behaviours (numbered tests in `tests/saved-food-ids.test.js`)

Ids
1. `isFoodId` accepts generated (`fduo0001`, `f` + 6..24 of `[0-9a-z]`) and derived (`f-` + 16 hex) ids and rejects everything else (uppercase, wrong length, no prefix, `__proto__`, `constructor`, HTML, spaces, numbers, null, objects, arrays, a foodKey).
2. `makeFoodId(1700000000000, () => 0.5)` is `'f' + 'loyw3v28' + 'i000'`; `rnd` 0 gives `0000`, a value just under 1 gives `zzzz`; always an `isFoodId` string without `-`; different inputs give different ids; never throws and still valid for NaN, undefined, strings, negative `now` and for `rnd` returning NaN/negative/over 1.
3. `legacyFoodId` golden values (hand-checkable FNV-1a 64, the algorithm was checked against the published vectors for `a`, `foobar` and the empty string): `Chili||Custom` no barcode is `f-a07ed5344605c4a3`; `Cheez-it Duo||Custom` is `f-c7e47751c795d5a1`; `=cmd|calc` is `f-ec77da65057a9fea`; empty name `||Custom` is `f-62eb5657dc2d9dd6`; `Rice bar||Custom` with barcode `5012345678900` is `f-8689d988c3fb7226` and with `4006381333931` is `f-6fcd96980c7234ac`.
4. `legacyFoodId` depends only on name, brand, source and barcode: numbers, `updatedAt`, `tag`, an existing `id` and other fields do not change it; brand or source changes do; a barcode with a leading zero (`036000291452`) gives the same id as without (`36000291452`) and an invalid barcode (7 digits, letters) behaves like none; foods with the same key and different barcodes get different ids; it is pure (frozen input, same result twice), returns `null` for non-objects and does not throw on hostile fields (objects whose `toString` throws are treated as `''`, `__proto__` names are just text).
Schema and migration
5. `SCHEMA_VERSION` is 9, `defaults().schemaVersion` 9, `STORAGE_KEY` is `macrodiary.v1`.
6. `migrate` of a v8 state gives every saved food `id === legacyFoodId(food)`, keeps order and every other field of every food, and is idempotent (`migrate(migrate(x))` deep-equals `migrate(x)`). Two devices migrating the same legacy food independently, with different surrounding lists and order, get the same id (the sync-duplication bug this feature must not cause).
7. A valid existing id is kept by `migrate`/`sanitize`; an invalid one (hostile, wrong type, too long, `__proto__`) is replaced by the derived id; foods are never dropped for a bad id.
8. Duplicates of one derived id inside one list collapse to the newest (tie: larger JSON), whichever order; same name with different barcodes both stay with different ids; same key twice with no barcode becomes one; the 100-food list and a 101-food legacy list keep every distinct food (the cap belongs to merging and adding, not to the migration).
9. Measures migrate: `measures['Cheez-it Duo||Custom']` moves to `measures[<id>]` with labels, grams and `updatedAt` intact and the old key is gone; when both exist they are merged by label (newer `updatedAt` wins, missing counts as 0); a key shared by two saved foods is copied to both ids; measures of a food that is not saved (`Oats|Quaker|OFF`) are untouched; with no saved foods `measures` is unchanged; empty and absent `measures` do not throw.
10. Copies are stamped: diary entries, recents, recipe-ingredient foods and plan foods matching exactly one saved food get `foodId`; a copy of a non-saved food (other source) gets none; a barcode-less copy of a key shared by two saved foods gets none; a copy WITH the barcode of one of two same-key saved foods gets that one's id; entry `id`, `updatedAt` and every other field are unchanged.
11. The fixtures survive: `tests/fixtures/state.json` and `backup.json` migrate to 9 with the same number of foods, entry ids per day, goals and the `Oats|Quaker|OFF` measures; the `=cmd|calc` food keeps every field and gains the derived id; in the backup the `Chili||Custom` measures end up under Chili's id.
11b. (`6b` in the test file) A save with NO `schemaVersion` loaded through `createStore` is migrated like any other: `core/store.js` builds `{ ...defaults(), ...saved }`, and `defaults()` already says 9, so a v1 save would skip every migration step. The implementer must make the v9 work (ids, measures, copy stamping) run for such a save too (compute the version before applying defaults, or do the work in `sanitize`); the test loads `state.json` and `backup.json` through the store.
12. `sanitize` and `sanitizeFood`: a valid `foodId` is kept on entries, recents, recipe and plan foods, an invalid one (HTML, `__proto__`, number, too long, uppercase) is removed; `sanitizeFood` turns a valid `id` into `foodId` and never outputs `id`.
13. A JSON round trip of migrated state is stable (`migrate(JSON.parse(JSON.stringify(m)))` deep-equals `m`).
Domain
14. `measuresKey`: `foodId` beats `id` beats `foodKey`; an invalid `foodId`/`id` is ignored (an entry-style id like `mh1abcd0001` falls through to the foodKey).
15. `unitsFor` offers a saved food's measures from `measures[id]`, a copy's from `measures[foodId]`; without an id it uses the foodKey bucket; when the food has an id the foodKey bucket is NOT used; another food's id bucket does not leak.
16. Recipes: `resolveGrams` and `recipeNutrition` use the measure of a linked saved food through `ingredient.food.foodId` (2 `box` of a 200 g box is 400 g, 2000 kcal at 500 kcal per 100 g), and fall back to the foodKey bucket when `foodId` is absent (then 2 x the 30 g serving = 60 g, as for any food whose measure is not found).
17. `addCustomFood`: new food gets `makeId()`, `updatedAt = now`, is first; the input object is not mutated (frozen input); replacing keeps the replaced food's id (and so its measures), the extra replaced ids get tombstones at `now`, others untouched; cap: the 101st food drops the oldest, no tombstone for it; an id used again clears its tombstone; invalid `makeId` output, duplicate id or unusable arguments return null with state unchanged; `makeId` is called once at most.
18. `updateCustomFood` by id: the id never changes on a rename; a foodKey string, an unknown id, `__proto__` and foods that have no id are not found (null, state unchanged); two same-name foods with different barcodes can each be edited and only the addressed one changes; measures are never touched.
Merge
19. Same id, different names: one food, newest wins as a whole, either argument order. Rename scenario: A renamed (newer) and B has the old name: one food with the new name in both orders; A renamed at 2000, B edited the numbers of the old name at 3000: B's whole record wins (old name, new numbers) in both orders; B's edit at 1500 (older): A wins.
20. Legacy convergence: A and B migrated the same legacy food independently, A renamed it: one food after merging in both orders. A new-app device merged with an old-app state that has the same food with no ids (and with the old name): one food, the newer one wins, both orders. Also with the old-app side holding its own newer edit.
21. Different ids with the same name/brand/source (twins) both survive; the same id twice inside one side collapses to the newest; a legacy food without id on one side and the same food with its derived id on the other is one food.
22. Cap and order: 101 distinct foods keep the 100 newest; order is `updatedAt` descending then `id` ascending; ties and argument order do not change the result; `preferLocal` still breaks `updatedAt` ties for the same id in favour of the first argument.
23. Tombstones for foods: tombstone later than or equal to the food's `updatedAt` hides it (either order); a food edited after the tombstone survives; a tombstone of a food id leaves entries and recipes with other ids alone; an old-app copy without id whose derived id is tombstoned stays deleted; tombstones are unioned as before.
24. Hostile ids in either side (`__proto__`, `constructor`, HTML, 10 000 characters, numbers, objects, arrays, empty, uppercase): every output food has an `isFoodId` id (the derived id for the hostile ones), no food is lost, no prototype pollution; measures buckets named `__proto__` or `constructor` are dropped (the result's `measures` keeps `Object.prototype` as its prototype).
25. Measures merge: an old-app bucket keyed by a saved food's foodKey is folded into the id bucket in either argument order (union by label, newer wins, old key removed); buckets of non-saved foods untouched; a bucket under an id with no saved food is kept as is.
26. Algebra: commutative, associative and idempotent for `custom`, `measures` and `tombstones` over a mixed set of states (new, legacy, renamed, twins, tombstoned).
27. Purity: frozen inputs (deep) are merged without throwing and unchanged.
Sync records
28. `toRecords`: the `custom` record carries each food's `id`, stamped with the newest food `updatedAt`; the `measures` record is keyed by ids for saved foods; other record keys and shapes are unchanged.
29. `applyRecords`: a `custom` record from an old-app device (no ids) gives derived ids; hostile ids are replaced; an old-app `measures` record keyed by foodKey is folded into the id bucket whichever of the two records arrives first; a record with a `foodId` on entries keeps valid ones and drops hostile ones.
30. Round trip: `toRecords(A)` applied to an empty state reproduces A's `custom`, `measures` and tombstones. A renamed on one device converges to one food on the other through records, in both directions.
Backup
31. `mergeRestore` of the v1/v8 backup fixture into current migrated data: no duplicate foods (the `=cmd|calc` food exists once), Chili is added with its derived id and its measures under that id, the Oats measure lists are unioned by label with this device winning ties.
32. `mergeRestore` of an old backup (no ids, no timestamps) after the food was renamed on this device: one food, this device's name (preferLocal; the backup food has the same derived id as the local food's original). Hostile ids in a backup are sanitised (valid ids kept, others derived), recents keep a valid `foodId` and lose a hostile one.
Static (WEAK, wording and wiring only)
33. `custom-food.js` uses `addCustomFood` and edits by `editing.id` (no `foodKey(editing)` edit key); `amount-picker.js` uses `measuresKey` and no longer reads `state.measures[foodKey(`; `add-food.js`, `plan-view.js` and `recipe-editor.js` pass `foodId`.
34. `sw.js` CACHE is greater than the previous main value (57); no new shipped file is added by the tests' requirements (the implementer adds any new file to `SHELL` as usual, `tests/sw.test.js` enforces it); `js/core/store.js` still uses `STORAGE_KEY`.
35. Docs (WEAK): KNOWN-ISSUES row 55 no longer says `Open` and says `Fixed`; DECISIONS has a decision after D52 that mentions saved food ids; `docs/SYNC.md` mentions the food `id`.

## Edge cases and hostile input

Empty name (a barcode-only food, `||Custom|<barcode>`), the same name/brand/source twice (with and without barcodes), exactly 100 and 101 foods, ids that are valid but shared by two foods, ids equal to a recipe or entry id in `tombstones`, hostile ids (`__proto__`, `constructor`, `toString`, HTML, very long, numbers, objects, arrays, empty, uppercase), foods from sync without an id arriving after the id version, old-app records and backups with and without timestamps, frozen input, purity of `legacyFoodId`/`makeFoodId`, measures lists that are not arrays or hold junk (existing filters stay), `custom` or `measures` missing or not the right type.

## Open questions

1. A copy of a saved food that arrives from an old-app device (entry, recipe or plan food) has no `foodId` and finds no saved measures (D-D accepted limit). Should the Amount screen look the food up by key at open time? Not decided; not tested.
2. Measures of a food dropped by the 100-food cap (or of a future deleted food) stay in `state.measures`. Pruning them is not specified.
3. Migration stamping of a copy that carries a barcode but whose same-key saved foods have none (or the reverse) is unspecified; only the cases in behaviour 10 are pinned.
4. A hand-made tombstone whose id equals a saved food's id and an entry's id would delete both (one shared namespace); judged unreachable in practice, not blocked.
5. Whether Recent (per-device, not synced) should show the old name after a rename stays as in D41.
6. The exact text of a recipe's per-serving calories on the Recipes tab is not specified here, so no headless item checks a recipe after migration; behaviour 16 covers the calculation.
