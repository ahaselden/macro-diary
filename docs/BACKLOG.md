# Feature backlog (priority order)

The queue of work, highest priority first. **When a feature is finished (PR merged), the next unchecked item is picked up.** Each implementation item is its own pull request and follows the [ship-feature skill](../.claude/skills/ship-feature/SKILL.md): plan, spec and failing tests by the test-designer, implement to green, PR, pr-reviewer. Background and reasoning: [VISION.md](VISION.md); stage history: [ROADMAP.md](ROADMAP.md); open problems: [KNOWN-ISSUES.md](KNOWN-ISSUES.md).

*Drafted on 2026-11-10 from VISION section 6 and the known issues. The order is a proposal; the owner can reorder it by editing this file.*

## How to use this list
0. **Nothing starts by itself.** Work begins only when the owner asks (for example "do the next backlog item"); an item counts as finished when the owner has merged its PR, because agents never merge. `CLAUDE.md` points every session here.
1. Take the first item whose box is not ticked and whose **Blocked by** is empty or done.
2. If an item is blocked (needs a decision or an account from the owner), skip it, say so in the PR or chat, and take the next one. Do not start work that needs an answer nobody has given.
3. When the PR merges, tick the box, add the PR number and today's date, and update the status in VISION section 2 and ROADMAP in the same change.
4. Items marked **plan and research only** produce a document for the owner to review (a docs-only PR); they never include code, and the owner's approval of the document is what creates the implementation item.
5. New ideas go at the bottom of "Later / unscheduled" until the owner places them.

## Later / unscheduled
- **Connect to Google Health / Fitbit: steps, workouts and sleep** *(owner 2026-11-12, widened 2026-11-13 to track steps, workouts and sleep)*. Bring steps, workouts (type, duration, calories burned) and sleep (time asleep, stages if available) and similar numbers from the owner's Fitbit or Google health data into the app so the day summary can show activity and sleep next to food, and so the calorie goal can later account for activity. Plan and research only first (like items 5 and 10), because the routes differ and some may not suit a web app with no backend of its own: the Fitbit Web API (OAuth sign-in; needs a registered app and a place for the secret, so the sync backend), Google's Health Connect (an Android on-device API, probably not reachable from a web page) and Google Fit (its web API may be retired). Questions to settle: which device or app the owner uses, whether a one-off CSV/export import is enough, privacy (health data is sensitive; see VISION principles), and how it affects the calorie goal, and where steps, workouts and sleep are stored and synced (a saved-shape change with its own spec). *(Facts above are from memory, not checked; the research must verify each provider's current terms.)*
- **Ids for saved foods (fixes KNOWN-ISSUES 55)** *(owner 2026-11-13)*. Saved custom foods are matched across devices by `name|brand|source` (`foodKey`), so renaming a food on one device while another still has the old name makes sync keep both, and the old name comes back as a duplicate (custom foods have no deletion record either). Give every saved food a stable `id` and merge by id, with a migration for existing foods (bump `SCHEMA_VERSION`, add a `migrate` step and a test that old data survives; `STORAGE_KEY` never changes), tombstones for deleted foods, saved measures keyed by food id instead of by name, and the same for the diary entries that copy a food. Also lets two foods with the same name and different barcodes be edited (today the editor refuses them). Needs a spec first; touches sync records, merge and backup, so the sync behaviour must be tested with old and new data together.
- **Android and iPhone testers** *(owner 2026-11-11: for the future, the headless browser is fine for now)*. Extend the browser-tester with real mobile engines: an Android emulator (Android Studio, virtual camera, real Chrome on Android; needs an install and about 10 GB) and iPhone Safari (WebKit): Playwright's WebKit build runs on Windows for the engine only, a real iPhone or iOS simulator needs a Mac or a device-cloud service (BrowserStack and similar, paid or trial). Real-phone items (camera quality, wake lock, install) stay on "Needs the owner" regardless.
