# Ship a feature ({{PROJECT}})

Roles are kept separate on purpose: the **test-designer** defines "done", **you** implement, the **pr-reviewer** and **browser-tester** judge. You may not edit the designer's tests to make them pass.

**No self-exemptions.** Small, UI-only or "obvious" changes follow every step too. What shrinks is the size of the spec (a few behaviours plus a checklist is enough, and source-text tests are acceptable when the project has no way to test the behaviour, if the spec says how weak they are), never whether the steps happen. Only {{OWNER}} can waive a step, in chat, for that change. If you skipped a step by mistake, say so and retrofit it (spec and tests written afterwards by a separate agent, verified to fail against the old code) rather than hiding it.

**Agents not registered?** New files in `.claude/agents/` only load when a session starts. If an agent is not found, run a `general-purpose` agent with "read `.claude/agents/<name>.md` and follow it exactly", restate its limits (test-designer: may not read the implementation, may write only `{{SPEC_DIR}}/` and `{{TEST_DIR}}/`; reviewer: read-only), and say in the PR that a stand-in was used.

**State what ran.** Every PR body lists which steps ran (spec first or retrofitted, designer tests, review, browser test) and which did not, and why.

1. **Plan.** Write a short plan (what, why, layers touched, UI or not). For anything user-visible or design-heavy, show it to {{OWNER}} first; when the request is ambiguous (for example which data source a feature should use), confirm the interpretation before building. `git fetch`, then create `feature/<short-name>` from `origin/{{MAIN}}` (not local `{{MAIN}}`, which is often behind; or from the current feature branch if the work builds on it).
2. **Spec and tests first.** Spawn the `test-designer` agent (fresh context, not a fork) with the plan. It writes `{{SPEC_DIR}}/<name>.md` and failing tests under `{{TEST_DIR}}/` only. Confirm yourself with `{{TEST_CMD}}` that the new tests fail for the right reason. Commit as its own commit: `Spec and failing tests for <name>`. Note the commit hash. Read the spec's "Existing tests this change will touch" list: those are the old tests and headless scenarios the feature will break; ask the designer (and, for scenarios, the browser-tester) to make those edits as soon as the build needs them, in step 3.
3. **Implement to green.** Implement in the right layers, in small commits (pure logic first). Do not edit those tests. If a test is wrong, say so in the PR description and send the question back to the test-designer (SendMessage) rather than fixing it yourself. Tests you add later are fine; say so in the commit message. Every edit the designer makes to a test after the spec commit (a bug in a fake, an existing test that pinned old code) goes into its OWN commit, `Test fix (designer): <what>`, never inside an implementation commit, so history shows who changed what; list each in the PR body. If you notice you must change a test to make progress, stop: that is a request to the designer, not an edit.
4. **Verify.** `{{TEST_CMD}}` all green. For UI changes a quick look that the page runs is enough here; the full browser test is step 6, so it only runs once. Update {{SHIPPING_CHECKS}} and {{DOCS_TO_UPDATE}}, and the spec's checklist. State what you could not verify.
5. **Push and open the PR** (a draft; {{OWNER}} authorised agents to do this): `git push -u origin feature/<name>`, then `gh pr create --draft --base {{MAIN}} --head feature/<name> --title ... --body-file ...`. The body has: what and why, a link to the spec, a test summary (counts, which came from the designer), changes to designer tests (should be "none"), and what is unverified. **Never** merge, never push `{{MAIN}}`, never force-push. {{ATTRIBUTION RULE}} If a push is blocked (for example by secret scanning), fix the cause (never bypass it): a fake value that looks like a real key is replaced, and unpushed commits are rebuilt locally, not force-pushed.
6. **Review and browser test, at the same time.** Start the `pr-reviewer` (read-only, on the branch with the spec path) and, when the change is user-visible, the `browser-tester` in the same message, so neither waits for the other. The reviewer never edits and the tester only adds scenario files, so they do not collide. The tester runs the spec's checklist with the network stubbed and reports PASS, FAIL or NOT TRIED per item, with known failures from `KNOWN-FAILURES.md` listed separately. Post both reports on the PR with `gh pr comment <n> --body-file <file>`. Then fix blocking findings and failures in new commits, push, and re-run ONLY what the fixes touched (the failed checklist items, or the reviewer for the changed files). A spec mistake the tester or reviewer finds goes back to the designer. The tester cannot cover a real device, installing the app, another browser engine or real third-party data: list those as unverified.
7. **Mark ready.** `gh pr ready <n>` once the reviewer has no blocking findings and the checklist passes; check `gh pr view <n> --json mergeStateStatus,statusCheckRollup`.
8. **Hand over, with the same report every time.** Tell {{OWNER}} the PR link, then this short table in plain words, one line per row, saying "not run" or "stand-in" honestly. Post the same table on the PR as a comment, then stop: {{OWNER}} merges.
   - **Spec and failing tests first:** who wrote them, and how many failed before the code.
   - **Implementation:** tests passing (count); designer tests changed (should be none, or listed).
   - **Review:** who ran it, the verdict, what was fixed, what was left.
   - **Browser test:** when it ran, what ran it (the agent, a stand-in, or the implementer directly), the commit it ran on, and PASS or FAIL per scenario.
   - **Owner actions:** what only {{OWNER}} can do, in order: merge; any console or settings change outside the repo; {{DEPLOY_NOTE}} before testing live or on a phone; the real-device checks from the spec.
   - **Not verified:** the real-device, real-data and other gaps.
   - Also say: whether local `{{MAIN}}` is behind `origin/{{MAIN}}`, the PR's real state, and any headless failures that are known and not caused by this change.

If a push or `gh` call is blocked by permissions, do not work around it: give {{OWNER}} the exact command to run.
